# Coordinated namespace CRUD over immutable content

Castle can preserve immutable content while a coordinated namespace gives people familiar files, folders, names, and current versions. The proposed extension puts current namespace state in a separate transactional database and stores source bytes and explicitly requested snapshots as ordinary Castle objects. Offline editing and concurrent multi-replica namespace mutation are not requirements. This brief specifies a proposed capability; it does not amend the delivered CAS contract or authorize implementation, data conversion, or deployment.

## 1. Existing behavior and the selected boundary

The delivered [CAS contract](cas-api.md) records content identities, immutable objects, journal events, and name sightings. Directory ingest retains each regular file's relative path, but does not capture empty directories, complete upload membership, a current-version pointer, or atomic folder restore. A name sighting is historical provenance, not a mutable namespace entry. The [CRDT contract](crdt-semantics.md) defines union of objects and journal events within a merge epoch; the [excision contract](content-excision.md) removes selected content by constructing a successor epoch and retiring the predecessor.

The selected architecture adds a coordinated namespace above those primitives. Content objects and journal events keep their existing schemas and union semantics. Namespace state has one authority and one mutation coordinator; it is explicitly not a CRDT. A CAS merge does not merge namespaces, resolve current versions, replay namespace commands, or confer authority on imported manifests. This avoids inventing distributed conflict semantics for a workflow that does not need them.

## 2. Authority, placement, and service ownership

The proposed namespace library accepts explicit resolved namespace and CAS roots, never a consuming workspace manifest. Its directory is a sibling of the CAS root or another caller-selected disjoint root; neither root contains the other. It contains `namespace.sqlite`, its SQLite sidecars, a stable coordinator lock, owned operation staging, and a bounded cutover recovery marker used during protected database replacement. It never adds arbitrary files or directories under a Castle CAS root: the existing strict inventory remains unchanged. Snapshots and any canonical request payload needed for durable recovery are ordinary CAS objects or protected namespace records, never new journal fields.

The namespace database owns current entry state, namespace identity, its policy version, its bound active CAS identity, revision, operation intents/results, explicit snapshot references, and dependency associations needed for excision. It is durable authority and cannot be reconstructed by guessing from all name sightings. Search indexes, path caches, exported trees, and rendered folder views are derived. Deleting the namespace database therefore loses current namespace authority even when source bytes survive; backup and restore must protect both authorities as a coherent unit.

One coordinator process owns all mutation for a namespace. API clients may be concurrent, but commands serialize under a stable, cross-process exclusive lock held through content publication and database commit. The database uses SQLite transactions with foreign keys enabled and durable commit settings (`synchronous=FULL`); its files live on local storage that supplies SQLite's locking and durability guarantees. Direct SQL writes and second independent writers are unsupported. Read clients use database read transactions or coordinator responses; consumer authorization governs every operation. Multi-host writers and network-filesystem databases are outside the initial design.

At open, the coordinator checks namespace format, identity, policy version, roots, and CAS binding. Unknown versions, inaccessible authority, changed bindings, and unresolved cutover state refuse normal service. The namespace has an immutable UUID, one root-directory UUID, a monotonic integer revision, and a recorded Unicode-data version for its name policy. Entry and operation identities are caller-supplied or coordinator-issued UUIDs and never recycled within that namespace. A namespace backup restored against a different CAS state is an explicit recovery action, not an automatic bootstrap.

## 3. Logical entry model

An entry has stable `entry_id`, immutable kind (`file` or `directory`), normalized display name, comparison key, parent-directory ID, structured metadata, and last-mutated revision. A file additionally has a current `cas_id`; a directory has no content identity. Names and paths are not entry identities. Replacing a file's bytes changes its content reference, not its entry ID; renaming or moving a directory preserves every descendant ID and content reference. Paths are computed by walking parent links from the root.

The root has no ordinary name or parent and cannot be renamed, moved, replaced, or deleted. Only live directories may be parents. Every live non-root entry has exactly one live parent and must be reachable from the root. There are no symlinks, hard links, mounts, or references that escape the namespace. Identical content may be referenced by several independent file entries; deleting one reference does not remove another's content.

Metadata is a JSON object of consumer-defined values, with a 64 KiB canonical UTF-8 encoded limit per entry, finite numbers, unique keys, and no hidden content-body field. Content-dependent metadata belongs to the same authorized protection domain as its source. Metadata can describe provenance or original filesystem attributes, but these are annotations, not promises to reproduce host ownership, permissions, ACLs, timestamps, or extended attributes. Kind, identity, parent, name, and content references remain typed fields rather than metadata keys.

## 4. Names, paths, and tree validation

Names use a fixed portable application policy: normalize display names to Unicode NFC; compare siblings using NFC of Unicode casefold of the normalized name. The recorded Unicode-data version fixes the behavior for the namespace. Names are nonempty, at most 255 UTF-8 bytes after normalization, and exclude slash, backslash, NUL, control characters, and the exact components `.` and `..`. The root is the sole exception to having a name. A unique index enforces `(live_parent_id, comparison_key)` for live entries. Two case or normalization variants cannot coexist in the same directory. Case-only renames of an entry are allowed when the resulting key belongs to that same entry.

Mutation APIs use entry IDs and parent IDs. An optional path interface accepts only relative component sequences, applies the same normalization, and refuses absolute paths, empty interior components, traversal, and ambiguous resolution. Upload paths follow that policy before admission, so a folder with colliding names is refused as a unit rather than silently renamed. OS case behavior never determines namespace identity. Exports must separately reject destination collisions and unsafe filesystem links; they cannot weaken the namespace policy.

Move validates that the destination is a live directory and not the moved directory or any of its descendants. Validation and publication occur in the same mutation transaction under the coordinator lock; no client-side check is authoritative. Foreign keys, uniqueness constraints, and explicit reachability/cycle checks jointly protect the tree. Moving into a deleted parent, moving root, replacing a directory with a file, and silently overwriting a sibling all refuse. Rename plus move is one atomic operation updating parent and name together.

## 5. CRUD and command contract

Every mutation includes namespace identity, expected namespace revision, and an idempotency UUID. A canonical request fingerprint includes operation kind, targeted IDs, normalized values, content identities, metadata, and expected revision. Coarse namespace revisions are intentional: a stale command refuses with the actual revision, and the client refreshes before resubmitting with a new operation UUID. This initially favors simple correctness over disjoint-edit parallelism.

| Command | Proposed atomic effect |
|---|---|
| Create directory | Add one empty directory under an existing live parent. |
| Create file | Add one file referencing verified, durably ingested content. |
| Read/list/resolve | Read one namespace revision; return stable IDs, current content references, and authorized metadata. |
| Replace content | Set an existing file's current content reference after durable CAS ingest; preserve its identity and name. |
| Set metadata | Replace the complete metadata object, avoiding an unspecified field-patch language. |
| Rename/move | Update one entry's name and parent together; preserve identity and descendants. |
| Delete entry | Remove a file or empty directory from the live view. |
| Delete subtree | Explicitly remove a directory and all live descendants as one transaction; ordinary delete never recurses implicitly. |
| Import folder | Admit a validated complete path-to-content mapping and explicit directories as one namespace transaction; existing-name collisions refuse. |
| Snapshot | Persist a canonical immutable view and publish an explicit snapshot reference. |

A successful mutation advances the namespace revision once and commits affected entries, the operation result, and dependency changes together. There is no success response before durable commit. Failed preconditions publish no namespace change. Identical retried requests return their durable outcome before considering the now-stale expected revision; reuse of an operation UUID for a different canonical request refuses. Operation identities remain reserved permanently; full results and request payloads may be retained only through an explicitly recorded retry window. After that window a retired token refuses rather than replaying its command. The initial retry window is seven days; expiration is an explicit maintenance action, never a prerequisite to correctness or confidentiality purge.

Deletion marks affected entries non-live and preserves identity reservation. It does not unlink CAS bytes, delete journal sightings, automatically excise content, or claim that historical snapshots no longer disclose the deleted name. There is no initial undelete operation; recreating an entry allocates a new ID. Sensitive deleted metadata and operation payloads participate in explicit purge and retention, rather than acquiring accidental permanent retention through a soft-delete table.

## 6. Durable publication, optimistic concurrency, and recovery

CAS and namespace SQLite have no shared transaction. The safe order is publish immutable content first, then publish its namespace reference. Under the coordinator lock, a command first checks idempotency and revision, validates its entire shape and authority binding, and durably records a prepared intent containing its canonical request and required content bindings. File bytes are durably staged in the protected namespace operation area before the prepared intent commits. The command acknowledges success only after the final namespace transaction, never merely after staging.

The coordinator ingests required content through Castle, verifies returned identities against the staged bytes, and then opens a short `BEGIN IMMEDIATE` transaction. It rechecks binding, expected revision, tree/name constraints, and the prepared intent, applies all namespace updates, records the terminal result, and commits. It subsequently disposes of owned staging. If CAS succeeds and the namespace transaction fails, the objects may remain unreferenced; they are not falsely presented as live files and are not deleted automatically. Unreferenced content is a known consequence of this publication order, handled through separately authorized retention/excision.

After a process crash, the OS releases the coordinator lock; a timeout is not authority to steal a lock from a living process. On reopen, outstanding intents block new mutations. Recovery verifies staging and every durable CAS binding and revalidates the original preconditions, then either completes the original command once or records a terminal failure without a namespace change. Missing or corrupt required staging/content is a failure, never permission to fabricate bytes. A committed outcome always wins over a leftover intent or temporary artifact; recovery returns that outcome and cleans only operation-owned staging. Failure after commit but before response is therefore safely retryable. Read transactions see complete states, not partially applied subtree operations.

Namespace recovery is not CAS repair. Before resuming an intent or publishing any reference, validate the backing CAS object/journal/index agreement and lifecycle. Current CAS ingest publishes an object before journal append, and abrupt termination can bypass its cleanup or interrupt the append. CAS-owned temporary residue, unjournaled objects, corrupt bytes, or a torn journal therefore enter a blocked storage-recovery state; the coordinator neither deletes that residue by guessing nor marks the command failed and reopens service. A separately specified, qualified CAS repair path is a prerequisite if the implementation promises automatic recovery from those interruptions. Until that path exists, failure is contained and requires explicit storage recovery. Tests must kill ingestion inside object publication and journal append, not only before or after a successful call.

Folder import is atomic at the namespace layer, not a filesystem snapshot taken against a live changing source. The intake layer must supply an immutable accepted upload inventory and exact bytes before the coordinator prepares the command. A changed input or incomplete intake refuses completion. Acceptance, namespace publication, and search reconciliation remain distinct observable stages; consumers report the stage they have actually completed.

## 7. Immutable manifests and bounded history

An explicit snapshot serializes a complete live tree in canonical UTF-8 JSON, including `schema: castle.namespace_snapshot.v1`, namespace UUID, policy/Unicode version, captured revision, root ID, protected CAS lineage/epoch binding, and entries sorted by entry UUID. Each entry records its kind, parent, normalized display name, metadata, and file content reference. Directory entries preserve empty folders. Canonical bytes use sorted object keys, no insignificant whitespace, finite JSON numbers, and one trailing newline; their SHA-256 identity is the snapshot identity. Serialization validates the whole tree and every selected content binding before ingest.

Snapshot commands hold the mutation lock while capturing revision R, writing the CAS object, and atomically publishing the snapshot catalog reference and result at revision R+1. The manifest states R, the tree it captured; it does not pretend to contain its own publication revision. No per-edit snapshot is produced by default. Current entry state is mutable authority, and historic views exist only where explicitly retained snapshots establish them. Snapshot publication follows the same intent and recovery contract as file content.

Snapshots are immutable descriptions for inspection and export, not editable head files or a way to override the live database. Restoring a snapshot into current namespace authority is outside the initial feature; it needs a later explicit contract for identity reuse, deleted entries, admission, and conflict checks. No timestamp selects a current version automatically, and a manifest from another epoch or namespace cannot become current state implicitly. Explicit snapshot deletion removes its live catalog reference; removing retained snapshot bytes or names requires the relevant content-retention/excision action. Consumers keep manifest dependencies separate from ordinary searchable documents so generic indexing does not treat a control artifact as source evidence.

## 8. CRDT and replica boundaries

Ordinary logical CRUD changes no Castle object bytes and removes no object/event from an active CAS epoch. The existing CAS projection therefore retains its union behavior. Namespace state, transaction history, counters, and mutable snapshot catalog are not included in that claim. A cloned CAS remains a same-epoch content replica; it is not an independently writable clone of the coordinated namespace. Consumers may copy immutable snapshots for inspection, but cannot merge edited copies or raw SQLite databases.

Content merged into the backing CAS is available for explicit admission but does not create namespace entries. External CAS merge/ingest is serialized against namespace mutation and lifecycle changes by the consumer's shared admission protocol; the namespace lock alone does not control a direct Castle caller. Divergent current-file selection, concurrent rename conflicts, and concurrent tree-cycle repair are deliberately absent: commands observe one ordered authority. Future offline editing would require a separately reviewed namespace CRDT, conflict semantics, causal history, and tree-invariant proof; it is not an upgrade obtained by removing the coordinator lock.

## 9. Logical deletion, confidential purge, and epoch cutover

The supported excision workflow remains coordinated and irreversible after retirement. Before excision the consumer stops all namespace and direct CAS admission, drains readers/open handles, resolves shared-content ownership, and records a durable private cutover intent in namespace authority with operation UUID and expected predecessor identity. Preparation enumerates dependencies in current entries, deleted metadata, manifests, snapshots, operation requests/results, CAS journal sighting fields and remotes, derived indexes, and consumer records. It identifies all content-bearing artifacts that disclose selected content or its forbidden metadata. A shared blob cannot be purged for one live owner while silently breaking another. Excision preserves the complete journal and remote records for retained content; it does not redact one forbidden historical filename attached to a retained blob. Such a requirement either selects that content and accounts for every owner, receives an explicit narrower custody claim, or refuses completion. New namespace-owned CAS ingestion uses opaque namespace/entry/operation IDs for source labels, paths, and batch values; user-facing names and upload paths live in protected namespace metadata/manifests. This minimizes new historical name leakage without claiming that existing sightings disappear.

A purge is not satisfied by removing only a file's current content reference. Historical manifests and namespace records may preserve its hash, name, metadata, or bytes. A replacement manifest is new content: it is not an in-place edit of the previous snapshot. The consumer explicitly chooses removal or sanitized replacement of affected retained snapshots and selects obsolete CAS payloads for excision along with source content. The database preserves only the non-content operation/entry identities needed for safety. Namespace cleanup requires protected database reconstruction where forensic absence is part of the claim, including old pages, SQLite journals, staging, and operation caches; merely deleting rows is insufficient. Backup and replica disposition remains separately reported custody work.

The recorded cutover intent blocks service through five durable stages, each of which resumes from its recorded authority instead of restarting the whole purge:

1. **Prepare dependencies.** Before retirement, persist validated sanitized recipes for every replacement snapshot, including retained entries/content identities and the selected snapshot catalog associations. Recipes exclude forbidden names and metadata and are protected operation data. Do not depend on reading selected predecessor manifests after retirement. The successor epoch is not yet known: Castle mints it inside excision.
2. **Complete Castle cutover.** Invoke excision and, after committed retirement, its forward recovery. A prepared successor is unavailable for ordinary ingestion. Only a completed active successor permits the next stage; record its validated identity and receipt in the private intent. Before retirement a failed operation leaves the predecessor authoritative; after retirement no namespace failure reactivates it.
3. **Publish replacement payloads.** While service stays blocked, create successor-bound snapshot manifests from the saved recipes, ingest them into the active successor, verify them, and persist their identities in the intent. Retry verifies recorded payloads or re-ingests identical bytes; it never repeats a completed excision or needs deleted old snapshots. CAS inconsistency blocks storage recovery here just as in ordinary command recovery.
4. **Commit live references.** One namespace transaction publishes the successor binding, retained references/dependency ownership, replacement snapshot associations, and selected entry/metadata removal. Record `references-published`, not purge completion. Retained source CAS identities remain unchanged; roots and epoch bindings change. Reference publication failure leaves service blocked and resumes this stage.
5. **Finish protected cleanup.** Reconstruct and validate a namespace database containing only retained authority and permitted recovery/idempotency identities. With all handles drained and the stable lock still held, checkpoint/close the old database, durably publish the fresh database by atomic replacement, remove owned old database/sidecars and operation staging/recipes, and independently check the required confidentiality boundary. A bounded selection-free marker binds namespace identity, cutover UUID, CAS predecessor/successor identities, database replacement generation, and cleanup stage outside the database being replaced. It carries no removed names, content identities, or recipe payloads. Marker and database generation must agree before service resumes; unknown residue refuses deletion. This supports forward recovery across replacement without relying on the removed database's selected data. Only after verified cleanup does the coordinator publish purge completion and reopen service.

No cross-database transaction or rollback of retirement is claimed. Durability failures and mismatched recovery state keep the namespace unavailable. Namespace format refinement must specify and qualify the exact replacement-marker publication protocol before implementation; the required stage/authority invariants above cannot be collapsed into one successful SQL transaction.

Old snapshots bound to the predecessor are unavailable through the current snapshot service after cutover. Retained snapshots explicitly carried forward need validated replacement manifests bound to the successor; their catalog associations advance atomically with other retained references. New same-epoch content replicas are made from the successor after the consumer completes cutover. Offline predecessors cannot merge into it, but can still hold removed bytes, and explicit re-ingestion remains a separate admission decision. Key destruction, external deletion, host remanence, and already disclosed plaintext are not supplied by this namespace capability.

## 10. Optional existing-store onboarding and format discovery

Existing stores remain usable without a namespace. Onboarding creates a new, separate namespace database; it does not rewrite objects, add journal fields, or infer current authority during ordinary reads. The namespace format is `castle.namespace.v1`; snapshots have their own discriminator. Consumers advertise optional namespace support and pass explicit resolved roots and feature versions. Missing namespace means the feature is absent, not an empty reconstructed tree. Unknown or inconsistent formats refuse interpretation; older CAS readers continue to see ordinary objects without gaining namespace semantics.

A caller-authorized reconstruction can seed a current selection from independent consumer authority, or an inventory from Castle sightings. An inventory retains all observed `(source_root_id, original_relpath, cas_id)` associations and labels its provenance as reconstructed observations, not an exact historical upload. Multiple versions at one path, cross-source root identity, normalization/case collisions, and unknown directory membership are reported before publication. No latest timestamp, first sighting, filename ordering, or batch label silently decides the current version. Explicit directory entries can preserve newly observed empty directories; backfill never invents past empty folders or filesystem attributes. The source corpus remains unchanged until the caller explicitly accepts the chosen namespace seed.

Name-policy or Unicode-data-version changes are deliberate namespace conversions: inventory collisions first, publish a validated new authority, and retain a recovery record. They are not a silent library-version effect. Initial feature addition needs no core CAS format migration. Pre-existing lifecycle enrollment, old journal conversion, namespace conversion, and encryption adoption are different operations with different authorization and proofs.

## 11. Ingest, retrieval, and encrypted-access consumers

Consumers retain their own identities, policy, and orchestration; Castle remains consumer-blind. An intake adapter supplies frozen upload inventories, source provenance, and exact bytes. A retrieval adapter indexes current admitted content and mirrors as rebuildable state, records which namespace revision it has reconciled, and resolves citations to immutable sources. A policy gateway authenticates principals, selects authorized stores/namespaces before addressing them, and never treats a mutable name or manifest as an access grant. Search lag after a namespace commit is visible and cannot be reported as rollback or lost ingest.

For encrypted deployments, the protection boundary includes namespace databases and sidecars, manifests, names, metadata, operation intents/results, staging, journals, indexes, and backups, not only source blobs. Current Castle provides neither encryption nor attested key custody. The namespace design does not grant a host process access simply because it is the service: an authorized execution adapter must supply protected I/O and transactional guarantees while unauthorized service processes see ciphertext. A plaintext SQLite database on a generally accessible host would violate that deployment model. The adapter's transaction, locking, restart, confidentiality, and key/session-lifetime properties need independent qualification; choosing or deploying the adapter is outside this brief.

Initially one namespace belongs to one protection domain and one bound CAS member. Cross-domain moves are not ordinary namespace moves: they require separately authorized ingest/reclassification and, where needed, excision. A gateway may render a principal-specific union of authorized namespaces without creating a global metadata index. Snapshot and export APIs inherit that same authorization and expose plaintext only to permitted destinations.

## 12. Acceptance evidence for future implementation

The following are proposed executable acceptance criteria, not results from this documentation task. Synthetic fixtures provide independent expected trees, byte identities, and dependency sets. Existing CAS merge and excision proofs remain required alongside namespace tests.

| Property | Falsifying behavioral check |
|---|---|
| Stable identity and deduplication | Rename/move preserve entry IDs; replacement changes only the content reference; two entries sharing bytes remain independent under logical delete. |
| Atomic CRUD | Force interruption during create, replacement, combined rename/move, folder import, and subtree delete; readers observe only the complete before or after tree. |
| Tree/name validity | Refuse missing/file/deleted parents, root mutations, descendant/self moves, normalization/case collisions, traversal, unsafe components, and sibling overwrite without any revision or live-row change. |
| Concurrency and idempotence | Concurrent commands with the same expected revision allow one ordered winner; identical retry returns one outcome; changed request under a reserved UUID refuses; expired UUID never reapplies a command. |
| Durable publication and recovery | Kill the process after staging, prepared intent, inside CAS publication/journal append, SQL commit, and response loss; prove no dangling live content reference, one namespace effect, correct terminal failure, explicit unreferenced-CAS residue, and blocked service for inconsistent backing storage. |
| Snapshot correctness | Independent traversal matches every manifest entry, empty directory, content identity, metadata value, and captured revision; repeated serialization of the same view is byte-identical; unsupported versions refuse. |
| Authority separation | Raw CAS merge introduces no live namespace entry; clone never creates another writer; namespace loss refuses current-state reconstruction; CAS same-epoch union laws remain unchanged. |
| Excision cutover | Drain admission and handles; persist sanitized recipes; remove selected sources plus dependent manifests; interrupt every stage including successor-manifest ingest and namespace database replacement; prove reference publication is not cleanup completion; independently scan retained authority and owned residue for forbidden identities and metadata, with journal/remotes dependencies included. |
| Onboarding truth | Ambiguous history and name collisions require explicit selection; reconstructed inventory is distinguished from complete upload snapshot; no invented empty directories or latest-version inference. |
| Protected adapter boundary | Unauthorized callers cannot read names or staging; inspect database sidecars, crash artifacts, backups, indexing, and response logs for plaintext; restart does not widen key or store access. |
| Platform qualification | Run coordinated SQLite/locking/recovery behavior on supported local macOS and Linux filesystems; no claim of network-storage or multi-host qualification follows. |

Manual acceptance judges whether the name policy, explicit subtree deletion, stale-revision retry, seven-day retry window, and snapshot/export behavior match the intended document workflow. Confidential purge receipts must state their enforced boundary and external-copy obligations. Those judgments and real-store migration remain with the owner.

## 13. Scope and remaining boundary decisions

Included in the proposed initial feature are coordinated current-state CRUD, validated file/directory hierarchy, frozen folder import, explicit immutable snapshots, durable intent recovery, optional seed reconstruction, and integration points for excision and protected execution. Excluded are offline editing, distributed namespace merge, snapshot-to-current-state restore, a mounted filesystem, automatic per-edit revision archives, automatic garbage collection, physical erasure, native filesystem metadata backup, cloud replication, authentication implementation, and an encryption implementation.

The architecture is selected; no alternative namespace engine or CRDT menu remains open. Future implementation must qualify the actual protected-I/O adapter, backing CAS interruption recovery, and protected database replacement protocol, and obtain caller decisions for any ambiguous existing-store seed or shared-content purge. These are deployment/custody inputs, not reasons to weaken transaction or confidentiality guarantees. Implementation needs a separately authorized contract refinement and delivery work; this draft leaves the shipped CAS API unchanged.
