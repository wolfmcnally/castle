# Coordinated namespace CRUD over immutable content

Castle can preserve immutable content while a coordinated namespace gives people familiar files, folders, names, and current versions. The proposed extension puts current namespace state in a separate transactional database and stores source bytes and explicitly requested snapshots as ordinary Castle objects. Offline editing and concurrent multi-replica namespace mutation are not requirements. This brief specifies a proposed capability; it does not amend the delivered CAS contract or authorize implementation, data conversion, or deployment.

## 1. Existing behavior and the selected boundary

The delivered [CAS contract](cas-api.md) records content identities, immutable objects, journal events, and name sightings. Directory ingest retains each regular file's relative path, but does not capture empty directories, complete upload membership, a current-version pointer, or atomic folder restore. A name sighting is historical provenance, not a mutable namespace entry. The [CRDT contract](crdt-semantics.md) defines union of objects and journal events within a merge epoch; the [excision contract](content-excision.md) removes selected content by constructing a successor epoch and retiring the predecessor.

The selected architecture adds a coordinated namespace above those primitives. Content objects and journal events keep their existing schemas and union semantics. Namespace state has one authority and one mutation coordinator; it is explicitly not a CRDT. A CAS merge does not merge namespaces, resolve current versions, replay namespace commands, or confer authority on imported manifests. This avoids inventing distributed conflict semantics for a workflow that does not need them.

## 2. Authority, placement, and service ownership

The proposed namespace library accepts explicit resolved namespace and CAS roots, never a consuming workspace manifest. Its directory is a sibling of the CAS root or another caller-selected disjoint root; neither root contains the other. It contains `namespace.sqlite`, its SQLite sidecars, a stable coordinator lock, owned operation staging, and a bounded cutover recovery marker used during protected database replacement. It never adds arbitrary files or directories under a Castle CAS root: the existing strict inventory remains unchanged. Snapshots and any canonical request payload needed for durable recovery are ordinary CAS objects or protected namespace records, never new journal fields.

The namespace database owns current entry state, namespace identity, its policy version, its bound active CAS identity, revision, operation intents/results, explicit snapshot references, and dependency associations needed for excision. It is durable authority and cannot be reconstructed by guessing from all name sightings. Search indexes, path caches, exported trees, and rendered folder views are derived. Deleting the namespace database therefore loses current namespace authority even when source bytes survive; backup and restore must protect both authorities as a coherent unit.

One coordinator process owns one namespace and its bound CAS member per protection domain. Concurrent requests are threads/tasks calling that coordinator in-process; they serialize under its admission mutex through content publication and database commit. A stable process-lifetime domain ownership lock and nested namespace ownership lock exclude competing coordinators; another process gets namespace-coordinator-busy, not an independently admitted SQL client. No IPC service is specified; callers needing cross-process requests must supply their own routing to the one coordinator. The database uses SQLite transactions with foreign keys enabled and durable commit settings (`synchronous=EXTRA`); its files live on local storage that supplies SQLite's locking and durability guarantees. Direct SQL writes and second independent writers are unsupported. All SQL reads go through the coordinator and use one admitted read transaction; consumer authorization governs every operation. Multi-host writers and network-filesystem databases are outside the initial design.

At open, the coordinator checks namespace format, identity, policy version, roots, and CAS binding. Unknown versions, inaccessible authority, changed bindings, and unresolved cutover state refuse normal service. The namespace has an immutable UUID, one root-directory UUID, a monotonic integer revision, and a recorded Unicode-data version for its name policy. Entry and operation identities are caller-supplied or coordinator-issued UUIDs and never recycled within that namespace. A namespace backup restored against a different CAS state is an explicit recovery action, not an automatic bootstrap.

## 3. Logical entry model

An entry has stable `entry_id`, immutable kind (`file` or `directory`), normalized display name, comparison key, parent-directory ID, structured metadata, and last-mutated revision. A file additionally has a current `cas_id`; a directory has no content identity. Names and paths are not entry identities. Replacing a file's bytes changes its content reference, not its entry ID; renaming or moving a directory preserves every descendant ID and content reference. Paths are computed by walking parent links from the root.

The root has no ordinary name or parent and cannot be renamed, moved, replaced, or deleted. Only live directories may be parents. Every live non-root entry has exactly one live parent and must be reachable from the root. There are no symlinks, hard links, mounts, or references that escape the namespace. Identical content may be referenced by several independent file entries; deleting one reference does not remove another's content.

Metadata is a JSON object of consumer-defined values, with a 64 KiB canonical UTF-8 encoded limit per entry, the bounded integer-only numeric policy in §16, unique keys, and no hidden content-body field. Content-dependent metadata belongs to the same authorized protection domain as its source. Metadata can describe provenance or original filesystem attributes, but these are annotations, not promises to reproduce host ownership, permissions, ACLs, timestamps, or extended attributes. Kind, identity, parent, name, and content references remain typed fields rather than metadata keys.

## 4. Names, paths, and tree validation

Names use a fixed portable application policy: normalize display names to Unicode NFC; compare siblings using NFC of Unicode casefold of the normalized name. The recorded Unicode-data version fixes the behavior for the namespace. Names are nonempty, at most 255 UTF-8 bytes after normalization, and exclude slash, backslash, NUL, control characters, and the exact components `.` and `..`. The root is the sole exception to having a name. A unique index enforces `(live_parent_id, comparison_key)` for live entries. Two case or normalization variants cannot coexist in the same directory. Case-only renames of an entry are allowed when the resulting key belongs to that same entry.

Mutation APIs use entry IDs and parent IDs. An optional path interface accepts only relative component sequences, applies the same normalization, and refuses absolute paths, empty interior components, traversal, and ambiguous resolution. Upload paths follow that policy before admission, so a folder with colliding names is refused as a unit rather than silently renamed. OS case behavior never determines namespace identity. Exports must separately reject destination collisions and unsafe filesystem links; they cannot weaken the namespace policy.

Move validates that the destination is a live directory and not the moved directory or any of its descendants. Validation and publication occur in the same mutation transaction under the coordinator lock; no client-side check is authoritative. Foreign keys, uniqueness constraints, and explicit reachability/cycle checks jointly protect the tree. Moving into a deleted parent, moving root, replacing a directory with a file, and silently overwriting a sibling all refuse. Rename plus move is one atomic operation updating parent and name together.

## 5. CRUD and command contract

Every mutation includes namespace identity, expected namespace revision, and an idempotency UUID. A canonical request fingerprint includes operation kind, targeted IDs, normalized values, content identities, metadata, and expected revision. Coarse namespace revisions are intentional: a stale command refuses with the actual revision, and the client refreshes before resubmitting with a new operation UUID. This initially favors simple correctness over disjoint-edit parallelism.

| Command | Proposed atomic effect |
|---|---|
| Create directory | Add one empty directory under an existing live parent. |
| Create file | Add one file referencing verified, durably ingested content. |
| Read/list/resolve | Read one namespace revision; return stable IDs, current content references, and authorized metadata. |
| Replace content | Set an existing file's current content reference after durable CAS ingest; preserve its identity and name. |
| Set metadata | Replace the complete metadata object, avoiding an unspecified field-patch language. |
| Rename/move | Update one entry's name and parent together; preserve identity and descendants. |
| Duplicate file/subtree | Copy a frozen file or complete directory tree with an exact fresh-ID map, sharing immutable CAS content; publish all copied entries atomically. |
| Delete entry | Remove a file or empty directory from the live view. |
| Delete subtree | Explicitly remove a directory and all live descendants as one transaction; ordinary delete never recurses implicitly. |
| Import folder | Admit a validated complete path-to-content mapping and explicit directories as one namespace transaction; existing-name collisions refuse. |
| Snapshot | Persist a canonical immutable view and publish an explicit snapshot reference. |

A successful mutation advances the namespace revision once and commits affected entries, the operation result, and dependency changes together. There is no success response before durable commit. Failed preconditions publish no namespace change. Identical retried requests return their durable outcome before considering the now-stale expected revision; reuse of an operation UUID for a different canonical request refuses. Operation identities remain reserved permanently; full results and request payloads may be retained only through an explicitly recorded retry window. After that window a retired token refuses rather than replaying its command. The initial retry window is seven days; expiration is an explicit maintenance action, never a prerequisite to correctness or confidentiality purge.

Deletion marks affected entries non-live and preserves identity reservation. It does not unlink CAS bytes, delete journal sightings, automatically excise content, or claim that historical snapshots no longer disclose the deleted name. There is no initial undelete operation; recreating an entry allocates a new ID. Sensitive deleted metadata and operation payloads participate in explicit purge and retention, rather than acquiring accidental permanent retention through a soft-delete table.

## 6. Durable publication, optimistic concurrency, and recovery

CAS and namespace SQLite have no shared transaction. The safe order is publish immutable content first, then publish its namespace reference. Under the coordinator lock, a command first checks idempotency and revision, validates its entire shape and authority binding, and durably records a prepared intent containing its canonical request and required content bindings. File bytes are durably staged in the protected namespace operation area before the prepared intent commits. The command acknowledges success only after the final namespace transaction, never merely after staging.

The coordinator ingests required content through Castle, verifies returned identities against the staged bytes, and then opens a short `BEGIN IMMEDIATE` transaction. It rechecks binding, expected revision, tree/name constraints, and the prepared intent, applies all namespace updates, records the terminal result, and commits. It subsequently disposes of owned staging. If CAS succeeds and the namespace transaction fails, the objects may remain unreferenced; they are not falsely presented as live files and are not deleted automatically. Unreferenced content is a known consequence of this publication order, handled through separately authorized retention/excision.

After a process crash, the OS releases the coordinator lock; a timeout is not authority to steal a lock from a living process. On reopen, outstanding intents block new mutations. Recovery verifies staging and every durable CAS binding and revalidates the original preconditions, then either completes the original command once or records a terminal failure without a namespace change. Missing or corrupt required staging/content is a failure, never permission to fabricate bytes. A committed outcome always wins over a leftover intent or temporary artifact; recovery returns that outcome and cleans only operation-owned staging. Failure after commit but before response is therefore safely retryable. Read transactions see complete states, not partially applied subtree operations.

Namespace recovery is not CAS repair. Before resuming an intent or publishing any reference, validate the backing CAS object/journal/index agreement and lifecycle. Current CAS ingest publishes an object before journal append, and abrupt termination can bypass its cleanup or interrupt the append. CAS-owned temporary residue, unjournaled objects, corrupt bytes, or a torn journal therefore enter a blocked storage-recovery state; the coordinator neither deletes that residue by guessing nor marks the command failed and reopens service. A separately specified, qualified CAS repair path is a prerequisite if the implementation promises automatic recovery from those interruptions. Until that path exists, failure is contained and requires explicit storage recovery. Tests must kill ingestion inside object publication and journal append, not only before or after a successful call.

Folder import is atomic at the namespace layer, not a filesystem snapshot taken against a live changing source. The intake layer must supply an immutable accepted upload inventory and exact bytes before the coordinator prepares the command. A changed input or incomplete intake refuses completion. Acceptance, namespace publication, and search reconciliation remain distinct observable stages; consumers report the stage they have actually completed.

## 7. Immutable manifests and bounded history

An explicit snapshot serializes a complete live tree in canonical UTF-8 JSON, including `schema: castle.namespace_snapshot.v1`, namespace UUID, policy/Unicode version, captured revision, root ID, protected CAS lineage/epoch binding, and entries sorted by entry UUID. Each entry records its kind, parent, normalized display name, metadata, and file content reference. Directory entries preserve empty folders. Canonical bytes use the exact Unicode-scalar key order, UTF-8/control escaping, bounded integers and one trailing newline specified in §16; their SHA-256 identity is the snapshot identity. Serialization validates the whole tree and every selected content binding before ingest.

Snapshot commands hold the mutation lock while capturing revision R, writing the CAS object, and atomically publishing the snapshot catalog reference and result at revision R+1. The manifest states R, the tree it captured; it does not pretend to contain its own publication revision. No per-edit snapshot is produced by default. Current entry state is mutable authority, and historic views exist only where explicitly retained snapshots establish them. Snapshot publication follows the same intent and recovery contract as file content.

Snapshots are immutable descriptions for inspection and export, not editable head files or a way to override the live database. Restoring a snapshot into current namespace authority is outside the initial feature; it needs a later explicit contract for identity reuse, deleted entries, admission, and conflict checks. No timestamp selects a current version automatically, and a manifest from another epoch or namespace cannot become current state implicitly. Explicit snapshot deletion removes its live catalog reference; removing retained snapshot bytes or names requires the relevant content-retention/excision action. Consumers keep manifest dependencies separate from ordinary searchable documents so generic indexing does not treat a control artifact as source evidence.

## 8. CRDT and replica boundaries

Ordinary logical CRUD changes no Castle object bytes and removes no object/event from an active CAS epoch. The existing CAS projection therefore retains its union behavior. Namespace state, transaction history, counters, and mutable snapshot catalog are not included in that claim. A cloned CAS remains a same-epoch content replica; it is not an independently writable clone of the coordinated namespace. Consumers may copy immutable snapshots for inspection, but cannot merge edited copies or raw SQLite databases.

Content merged into the backing CAS is available for explicit admission but does not create namespace entries. External CAS merge/ingest is serialized against namespace mutation and lifecycle changes by the consumer's shared admission protocol; the namespace lock alone does not control a direct Castle caller. Divergent current-file selection, concurrent rename conflicts, and concurrent tree-cycle repair are deliberately absent: commands observe one ordered authority. Future offline editing would require a separately reviewed namespace CRDT, conflict semantics, causal history, and tree-invariant proof; it is not an upgrade obtained by removing the coordinator lock.

## 9. Logical deletion, confidential purge, and epoch cutover

The supported excision workflow remains coordinated and irreversible after retirement. Before excision the consumer stops all namespace and direct CAS admission, drains readers/open handles, resolves shared-content ownership, and records a durable private cutover intent in namespace authority with operation UUID and expected predecessor identity. Preparation enumerates dependencies in current entries, deleted metadata, manifests, snapshots, operation requests/results, CAS journal sighting fields and remotes, derived indexes, and consumer records. It identifies all content-bearing artifacts that disclose selected content or its forbidden metadata. A shared blob cannot be purged for one live owner while silently breaking another. Excision preserves the complete journal and remote records for retained content; it does not redact one forbidden historical filename attached to a retained blob. Such a requirement either selects that content and accounts for every owner, receives an explicit narrower custody claim, or refuses completion. New namespace-owned CAS ingestion uses opaque namespace/entry/operation IDs for source labels, paths, and batch values; user-facing names and upload paths live in protected namespace metadata/manifests. This minimizes new historical name leakage without claiming that existing sightings disappear.

A purge is not satisfied by removing only a file's current content reference. Historical manifests and namespace records may preserve its hash, name, metadata, or bytes. A replacement manifest is new content: it is not an in-place edit of the previous snapshot. The consumer explicitly chooses removal or sanitized replacement of affected retained snapshots and selects obsolete CAS payloads for excision along with source content. The database preserves only the non-content operation/entry identities needed for safety. Namespace cleanup requires protected database reconstruction where forensic absence is part of the claim, including old pages, SQLite journals, staging, and operation caches; merely deleting rows is insufficient. Backup and replica disposition remains separately reported custody work.

The recorded cutover intent blocks service through five durable stages, each of which resumes from its recorded authority instead of restarting the whole purge:

1. **Prepare dependencies.** Before retirement, persist validated sanitized recipes for every replacement snapshot, including retained entries/content identities and the selected snapshot catalog associations. Recipes exclude forbidden names and metadata and are protected operation data. Do not depend on reading selected predecessor manifests after retirement. The successor epoch is not yet known: Castle mints it inside excision.
2. **Complete Castle cutover.** Invoke excision and, after committed retirement, its forward recovery. A prepared successor is unavailable for ordinary ingestion. Only a completed active successor permits the next stage; record its validated identity and receipt in the private intent. Before retirement a failed operation leaves the predecessor authoritative; after retirement no namespace failure reactivates it.
3. **Publish replacement payloads.** While service stays blocked, create successor-bound snapshot manifests from the saved recipes, ingest them into the active successor, verify them, and persist their identities in the intent. Retry verifies recorded payloads or re-ingests identical bytes; it never repeats a completed excision or needs deleted old snapshots. CAS inconsistency blocks storage recovery here just as in ordinary command recovery.
4. **Commit live references.** One namespace transaction publishes the successor binding, retained references/dependency ownership, replacement snapshot associations, and selected entry/metadata removal. Record `references-published`, not purge completion. Retained source CAS identities remain unchanged; roots and epoch bindings change. Reference publication failure leaves service blocked and resumes this stage.
5. **Finish protected cleanup.** Reconstruct and validate a namespace database containing only retained authority and permitted recovery/idempotency identities. With all handles drained and the stable lock still held, checkpoint/close the old database, durably publish the fresh database by atomic replacement, remove owned old database/sidecars and operation staging/recipes, and independently check the required confidentiality boundary. A bounded selection-free marker binds namespace identity, cutover UUID, CAS predecessor/successor identities, database replacement generation, and cleanup stage outside the database being replaced. It carries no removed names, content identities, or recipe payloads. Marker and database generation must agree before service resumes; unknown residue refuses deletion. This supports forward recovery across replacement without relying on the removed database's selected data. Only after verified cleanup does the coordinator publish purge completion and reopen service.

No cross-database transaction or rollback of retirement is claimed. Durability failures and mismatched recovery state keep the namespace unavailable. Section 18 specifies the exact replacement-marker publication protocol for future implementation and qualification; the required stage/authority invariants above cannot be collapsed into one successful SQL transaction.

Old snapshots bound to the predecessor are unavailable through the current snapshot service after cutover. Retained snapshots explicitly carried forward need validated replacement manifests bound to the successor; their catalog associations advance atomically with other retained references. New same-epoch content replicas are made from the successor after the consumer completes cutover. Offline predecessors cannot merge into it, but can still hold removed bytes, and explicit re-ingestion remains a separate admission decision. Key destruction, external deletion, host remanence, and already disclosed plaintext are not supplied by this namespace capability.

## 10. Optional existing-store onboarding and format discovery

Existing stores remain usable without a namespace. Onboarding creates a new, separate namespace database; it does not rewrite objects, add journal fields, or infer current authority during ordinary reads. The namespace format is `castle.namespace.v1`; snapshots have their own discriminator. Consumers advertise optional namespace support and pass explicit resolved roots and feature versions. Missing namespace means the feature is absent, not an empty reconstructed tree. Unknown or inconsistent formats refuse interpretation; older CAS readers continue to see ordinary objects without gaining namespace semantics.

A caller-authorized reconstruction can seed a current selection from independent consumer authority, or an inventory from Castle sightings. An inventory retains all observed `(source_root_id, original_relpath, cas_id)` associations and labels its provenance as reconstructed observations, not an exact historical upload. Multiple versions at one path, cross-source root identity, normalization/case collisions, and unknown directory membership are reported before publication. No latest timestamp, first sighting, filename ordering, or batch label silently decides the current version. Explicit directory entries can preserve newly observed empty directories; backfill never invents past empty folders or filesystem attributes. The source corpus remains unchanged until the caller explicitly accepts the chosen namespace seed.

Name-policy or Unicode-data-version changes are deliberate namespace conversions: inventory collisions first, publish a validated new authority, and retain a recovery record. They are not a silent library-version effect. Initial feature addition needs no core CAS format migration. Pre-existing lifecycle enrollment, old journal conversion, namespace conversion, and encryption adoption are different operations with different authorization and proofs.

## 11. Ingest, retrieval, and encrypted-access consumers

Consumers retain their own identities, policy, and orchestration; Castle remains consumer-blind. An intake adapter supplies frozen upload inventories, source provenance, and exact bytes. A retrieval adapter indexes current admitted content and mirrors as rebuildable state, records which namespace revision it has reconciled, and resolves citations to immutable sources. A policy gateway authenticates principals, selects authorized stores/namespaces before addressing them, and never treats a mutable name or manifest as an access grant. Search lag after a namespace commit is visible and cannot be reported as rollback or lost ingest.

For encrypted deployments, the protection boundary includes namespace databases and sidecars, manifests, names, metadata, operation intents/results, staging, journals, indexes, and backups, not only source blobs. Current Castle provides neither encryption nor attested key custody. The namespace design does not grant a host process access simply because it is the service: an authorized execution adapter must supply protected I/O and transactional guarantees while unauthorized service processes see ciphertext. A plaintext SQLite database on a generally accessible host would violate that deployment model. The environment capability's transaction, locking, restart, confidentiality, and key/session-lifetime properties need independent qualification; choosing or deploying the environment is outside this brief. Section 19 distinguishes explicitly unprotected use from protected capability admission without introducing an in-process replacement for delivered CAS I/O.

Initially one namespace belongs to one protection domain and one bound CAS member. Cross-domain moves are not ordinary namespace moves: they require separately authorized ingest/reclassification and, where needed, excision. A gateway may render a principal-specific union of authorized namespaces without creating a global metadata index. Snapshot and export APIs inherit that same authorization and expose plaintext only to permitted destinations.

## 12. Acceptance evidence for future implementation

The following are proposed executable acceptance criteria, not results from this documentation task. Synthetic fixtures provide independent expected trees, byte identities, and dependency sets. Existing CAS merge and excision proofs remain required alongside namespace tests.

| Property | Falsifying behavioral check |
|---|---|
| Stable identity and deduplication | Rename/move preserve entry IDs; replacement changes only the content reference; two entries sharing bytes remain independent under logical delete. |
| Atomic CRUD | Force interruption during create, replacement, combined rename/move, folder import, and subtree delete; readers observe only the complete before or after tree. |
| Tree/name validity | Refuse missing/file/deleted parents, root mutations, descendant/self moves, normalization/case collisions, traversal, unsafe components, and sibling overwrite without any revision or live-row change. |
| Concurrency and idempotence | Concurrent commands with the same expected revision allow one ordered winner; identical retry returns one outcome; changed request under a reserved UUID refuses; expired UUID never reapplies a command. |
| Durable publication and recovery | Kill the process after staging, prepared intent, inside CAS publication/journal append, SQL commit, and response loss; prove no dangling live content reference, one namespace effect, correct terminal failure, explicit unreferenced-CAS residue, and blocked service for inconsistent backing storage. |
| Snapshot correctness | Independent traversal matches every manifest entry, empty directory, content identity, metadata value, and captured revision; repeated serialization of the same view is byte-identical; unsupported versions refuse. |
| Authority separation | Raw CAS merge introduces no live namespace entry; clone never creates another writer; namespace loss refuses current-state reconstruction; CAS same-epoch union laws remain unchanged. |
| Excision cutover | Drain admission and handles; persist sanitized recipes; remove selected sources plus dependent manifests; interrupt every stage including successor-manifest ingest and namespace database replacement; prove reference publication is not cleanup completion; independently scan retained authority and owned residue for forbidden identities and metadata, with journal/remotes dependencies included. |
| Onboarding truth | Ambiguous history and name collisions require explicit selection; reconstructed inventory is distinguished from complete upload snapshot; no invented empty directories or latest-version inference. |
| Protected adapter boundary | Unauthorized callers cannot read names or staging; inspect database sidecars, crash artifacts, backups, indexing, and response logs for plaintext; restart does not widen key or store access. |
| Platform qualification | Run coordinated SQLite/locking/recovery behavior on supported local macOS and Linux filesystems; no claim of network-storage or multi-host qualification follows. |

Manual acceptance judges whether the name policy, explicit subtree deletion, stale-revision retry, seven-day retry window, and snapshot/export behavior match the intended document workflow. Confidential purge receipts must state their enforced boundary and external-copy obligations. Those judgments and real-store migration remain with the owner.

## 13. Scope and remaining boundary decisions

Included in the proposed initial feature are coordinated current-state CRUD, validated file/directory hierarchy, frozen folder import, explicit immutable snapshots, durable intent recovery, optional seed reconstruction, and integration points for excision and protected execution. Excluded are offline editing, distributed namespace merge, snapshot-to-current-state restore, a mounted filesystem, automatic per-edit revision archives, automatic garbage collection, physical erasure, native filesystem metadata backup, cloud replication, authentication implementation, and an encryption implementation.

The architecture is selected; no alternative namespace engine or CRDT menu remains open. Future implementation must qualify the actual protected-I/O adapter, backing CAS interruption recovery, and protected database replacement protocol, and obtain caller decisions for any ambiguous existing-store seed or shared-content purge. These are deployment/custody inputs, not reasons to weaken transaction or confidentiality guarantees. This refined specification leaves the shipped CAS API unchanged; runtime implementation and qualification remain separate authorized work.

## 14. Refined extension contract (specified, not delivered)

As of 2026-10-21, the following closed schemas refine this proposed extension. They are specifications for subsequent implementation, not claims that these symbols or commands exist in the shipped package. Existing ordinary CAS and excision APIs retain their delivered behavior. The operation tables below own exact shapes; earlier sections describe their rationale.

### 14.1 Scalar and authority types

| Type | Exact representation and constraints |
|---|---|
| NamespaceUUID | Lowercase canonical hyphenated RFC 4122 variant/version-4 UUID string, nonnil. Namespace, root, entry, operation, snapshot-reference and database-generation IDs use this type. Separate typed reservations prevent an entry ID being used as an operation reference; each pool never recycles IDs. |
| CasIdentity | The delivered StoreIdentity object with exactly store_id, lineage_id, epoch_id, generation and predecessor_epoch_id; validate its delivered relationship rules. Store identity is member-specific; a same-epoch replica cannot silently replace the bound member. |
| CasID | The delivered prefixed form sha256: followed by exactly 64 lowercase hexadecimal characters naming SHA-256 of complete payload bytes; size is a nonnegative integer within the safe integer bound below. Raw hexadecimal request fingerprints and marker image digests are separate 64-character digest fields, not CasIDs. A reference requires verified local durable object and journal/index agreement, not just syntactic validity. |
| Revision | Integer from 0 through 9007199254740991; booleans are not integers. Initialize at 0. Every successful mutation, including no-op rename/metadata replacement, advances exactly once. Refuse exhaustion before preparing a mutation; never wrap. |
| NamePolicy | Exactly policy_version: 1 and unicode_data_version: the exact supported Unicode data version supplied at creation and persisted unchanged. A runtime with different normalization/casefold data refuses open; conversion is outside ordinary execution. |
| Name | NFC display string with the §4 comparison rule; 1–255 UTF-8 bytes, no unpaired surrogate, slash, backslash, NUL, Unicode Cc control, or exact dot/dot-dot component. Unassigned/private-use scalars are not rejected merely by category. Root name and parent are null. No platform-specific trimming or implicit suffixing. |
| Metadata | JSON object, maximum 65536 canonical UTF-8 bytes excluding the record LF, depth at most 32 with the top-level object at depth 1 and only containers adding depth; string keys, no duplicate keys or invalid Unicode. Values are null, boolean, string, arrays, objects or integers in [-9007199254740991,9007199254740991]. Floating point, Decimal, NaN and infinity refuse; decimal application quantities can be strings. Metadata strings/keys are preserved exactly, not name-normalized. |
| ContentSpec | Closed object with cas_id and size. The caller supplies a separate authorized immutable byte source handle when the bytes need admission; its bytes must match both fields. Source handles/host paths never enter the canonical request or persisted manifest. Existing-object admission verifies the same binding under the coordinator. |
| EntryRecord | Exactly entry_id, kind, parent_id, name, metadata, cas_id, size and changed_revision. kind is file or directory. Files require CasID/size; directories require both null. The immutable root is a directory with null parent/name, empty metadata and no content. |

Roots are explicit resolved library arguments, never persisted paths or discovered through a request. The caller supplies the stable domain ownership-lock capability; two namespaces in the same protection domain cannot acquire separate coordinator ownership. CAS-only users in this domain route admitted work through this same coordinator; an independent cross-process direct writer is unsupported. All operations also receive an opaque caller-owned authorized protection-session handle. It is not serializable and is not an access grant embedded in a UUID, path or manifest. One coordinator owns one namespace and bound CAS member within one protection domain. Cross-domain relocation requires external authorized reclassification/ingest and optional excision; it has no Castle multi-domain commit or rollback guarantee.

### 14.2 Library, requests and results

The proposed public owners are project/castle/namespace.py for namespace calls and project/castle/cas_recovery.py for bounded publication. create_namespace(namespace_root, cas_root, session, request) returns NamespaceInfo; open_namespace(namespace_root, cas_root, session) returns NamespaceHandle; execute_namespace(handle, request, content_sources, excision_roots=None) returns MutationResult; read_namespace(handle, request) returns ReadResult; namespace_operation(handle, operation_id) returns OperationStatus; recover_namespace(namespace_root, cas_root, session, recovery_roots) returns RecoveryResult. content_sources is a mapping from declared CasID to an authorized immutable source handle; reject unused keys and missing sources when admission needs bytes. excision_roots is required exactly for kind excise and has exactly predecessor_root and successor_root; predecessor_root must equal the handle's resolved bound root. It is null for every other kind. recovery_roots is null for ordinary intent repair or has exactly predecessor_root, successor_root, operation_id, expected_predecessor and action (resume or abort-before-retirement) for cutover. The abort action is valid only under the pre-retirement proof below; no root comes from metadata. It can run while ordinary open refuses unresolved state. Handles never escape their session lifetime. These are typed functions over immutable request/result records, not an untyped arbitrary SQL/command plugin. Library public errors are NamespaceError with the closed code and safe typed fields in §14.3. Initialization is explicit and exclusive; opening missing authority never initializes it.

InitializeRequest has exactly schema: castle.namespace_initialize.v1, namespace_id, root_id, expected_cas: CasIdentity, policy: NamePolicy, protection: ProtectionMode. IDs must be distinct; an existing authority refuses initialization. NamespaceInfo has exactly schema: castle.namespace_info.v1, namespace_id, root_id, policy, cas: CasIdentity, revision, database_generation and protection: ProtectionMode. ### 14.3 Error and retry contract

Public NamespaceError contains exactly code, namespace_id (null if not safely established), operation_id (null for reads/pre-reservation rejection), actual_revision (null unless authorized and known), and effect (none, namespace-committed, or recovery-required). No free-form path, name, metadata, SQL, digest selection, backend exception or credential appears in an error message/log. Suppress exception chaining at the CLI boundary. A transport timeout/disconnect is an unknown response outcome, not a terminal NamespaceError; query/retry the same token before starting a new command.

Validation precedence is session/capabilities, safe explicit roots and stable ownership, namespace authority/version and current root lifecycle, closed request shape and normalization, existing token/fingerprint, expected CAS binding and revision, tree/content/dependency constraints, then durable publication. A complete normalized fingerprint can require reading the request's declared content descriptors but never re-reading a mutable source to define request identity. Malformed requests may be rejected without token reservation. Once a shape-valid token is reserved, success or domain-precondition rejection is durable and repeatable: store rejected outcomes without advancing namespace revision. Reserve/check the token and evaluate expected revision under the same exclusive coordinator admission. A same-token/same-fingerprint retry returns the retained durable outcome before stale-revision checks; concurrent identical retries join one operation. A same-token/different-fingerprint request never joins it. The fingerprint includes expected revision, namespace/member binding, kind and every normalized semantic argument; operation_id is the lookup key and excluded from fingerprint bytes.

A prepared/publishing token returns state prepared/publishing with next_action retry-same; a blocked service returns recovery-required, never an invented terminal failure. The seven-day retry window is measured from the recorded terminal completion UTC timestamp; a clock moving backward delays maintenance and never reactivates an expired token. Expire-results itself is idempotent and may not expire its own active token. Expiry removes canonical requests, results, error details and fingerprints; only the reserved operation UUID and retired state remain. A retired UUID refuses every later request without fingerprint comparison. This prevents API-level dictionary confirmation through a logically retained fingerprint. Ordinary expiry is not forensic cleanup: deleted payload/fingerprint bytes may remain in SQLite free pages until the separately fenced fresh-database purge. No secure-delete or physical-erasure claim follows. Confidential purge may remove selected request/result payloads before seven days and their fingerprints while preserving only the reserved token, marking it retired; this intentionally refuses replay rather than retaining forbidden data to satisfy the retry window. After an ambiguous response clients must inspect the original token; they must not infer permission to repeat an effect with a fresh token. No automatic retry of a partially completed epoch excision is a new excision.

## 15. Transaction, consistency and durable acknowledgment

All namespace operations have ACID reliability within this single-coordinator/protection-domain envelope, including recursive copy/delete and snapshot operations. Acquire the caller-owned stable domain ownership lock first, then the stable namespace coordinator lock, and hold both for the coordinator lifetime. No operation reacquires either lifetime lock under a CAS lock. Within that owner, the admission mutex serializes mutation, recovery, SQL read admission and lifecycle changes; its order is admission mutex then CAS stable locks in delivered deterministic order. Direct CAS work in this protection domain uses the owner's same admission mutex. Concurrent in-process callers can submit all requests; a competing coordinator process fails namespace-coordinator-busy before SQL access. No cross-process IPC service, multiple-coordinator database or distributed commit is implied.

All SQL reads are coordinator responses, never independent raw SQLite connections. Each ordinary read is admitted after prior outstanding recovery, holds the admission mutex through its single SQLite read transaction and observes one complete committed revision. SQL reads and mutations serialize; exported immutable content handles may outlive the SQL transaction but remain registered with the domain admission fence. Read authorization and active CAS binding are validated in that admission; at_revision, when nonnull, must equal the observed revision or conflict. A later call may observe a later revision. A read overlapping a mutation may linearize before or after its final SQL commit, never through its intermediate rows; a read starting after acknowledged success observes that commit or a later one. A caller exporting content retains an admitted read handle and immutable object identity until completion; excision/authority replacement closes admission and waits for every such handle to drain. Direct SQL readers are unsupported because they could bypass these fences and retain predecessor pages. Read-only operations do not increment the revision.

SQLite uses foreign_keys=ON, journal_mode=DELETE and synchronous=EXTRA; WAL is not used in v1. Every schema/intent/result/live-reference update uses an explicit transaction, never autocommit across multiple rows. Page size is recorded at creation and carried into fresh images; unknown/mismatched sidecars refuse. Before any SQLite open, inspect the replacement marker and establish the selected database file/sidecar ownership. Only then may the selected engine recover that file's own rollback journal and check namespace invariants; Castle does not hand-edit rollback journals. The adapter must qualify the selected journal mode, file/directory durability and locking on the actual local storage. The [pinned SQLite synchronous documentation](../docs/sqlite-synchronous.txt) distinguishes EXTRA's journal-unlink directory sync from FULL; read back all PRAGMA values (including synchronous=3) before service. Durability covers process loss and power loss only under the actual qualified filesystem/VFS/hardware flush guarantees, never merely a process-kill fixture. A successful SQLite commit without the required CAS evidence is insufficient. SQLITE_BUSY/timeout or uncertain commit after CAS publication does not make a terminal rejection: preserve the intent, block new admission and recover the actual SQL outcome. A provably rolled-back transaction may be retried under the same operation; an existing committed result always wins. A living unexpected raw connection is unsupported, not authority to delete its journal.

| Durable boundary | Authority and crash/retry rule |
|---|---|
| Before intent | Complete immutable staged bytes and a protected ownership recipe must be fsynced before a transaction stores prepared. Unreferenced pre-intent staging is collectible only by its independently durable owned receipt, never by directory-name resemblance. No live effect exists. |
| Prepared committed | Canonical request, fingerprint, original revision/binding, exact IDs, staging descriptors and recovery evidence are authoritative. Block later mutation/read admission until this operation is resolved. An earlier SQL read has already released the admission mutex before preparation; only its separately admitted immutable export handle may remain outstanding. No new SQL read observes uncertain publication. |
| Publishing | Bounded CAS publication runs first. Zero/partial/complete CAS effects are settled by §17, never by guessing. Namespace authority still represents the old tree. |
| Final SQL transaction | BEGIN IMMEDIATE rechecks request/binding/revision/tree, publishes all affected rows, dependencies, snapshot associations and committed result in one durable commit. This commit is ordinary mutation's linearization point; a rejection commits only the terminal error/token state. |
| Commit acknowledged | Success is emitted only after SQL commit durability and validated durable CAS effects. A lost response replays the same outcome. Failure removing staging after commit never changes committed into rejected; service blocks cleanup/recovery if confidential residue cannot be safely retired. |
| Restart | Acquire stable ownership, validate active binding, marker/generation and CAS recovery evidence, settle intents, and dispose only owned residue before admitting service. Never steal a live coordinator lock based on age. |

Atomicity is the complete namespace transition, not a fictitious distributed SQLite/CAS rollback. Durably published but unreferenced immutable blobs can survive an aborted namespace commit; they are discoverable retained CAS inventory, not dangling namespace references and not permission for automatic GC. Consistency includes rooted acyclic live trees, identity reservation, name uniqueness, valid content bindings and dependency closure. Isolation is serialization of accepted operations and one-revision read snapshots. Durability means an acknowledged outcome survives process termination and the adapter's qualified storage-failure model. Storage that cannot supply required fsync/atomicity refuses rather than weakening acknowledgment.

Excision is additionally fenced across its irreversible retirement. Before retirement an abort may preserve the old tree/epoch; after retirement service remains unavailable until forward recovery yields a complete successor and protected namespace cleanup. Partial stages are recovery-required, never a terminal rollback or successful purge. The operation linearizes for namespace clients when the final clean successor authority is durably made ready; no client can observe intermediate reference publication. CAS retirement is its separate internal point of no return and does not promise cross-domain atomicity. Session revocation blocks new plaintext access and acknowledgment; authorized recovery later resumes recorded effects without assuming the session stayed alive.

## 16. Canonical bytes and persisted relations

Canonical encoding is defined independently of a JSON library: valid Unicode scalar strings only; object keys ordered by lexicographic Unicode scalar value; array order retained unless a table explicitly requires sorting; encode UTF-8 without BOM, non-ASCII characters unescaped, slash unescaped, quote/backslash escaped, and every U+0000–U+001F encoded as lowercase six-character backslash-u plus four hex digits. No short newline/tab escape alternatives. Integers use base-10 ASCII with optional minus only, no leading zero or plus, and zero is exactly 0. Floats, exponent syntax, negative zero, duplicate keys and out-of-range integers refuse on canonical input. Object separators are comma/colon with no whitespace; append exactly one LF to the complete top-level record. Parsers may accept request JSON whitespace/order but canonicalize semantic values before hashing; persisted canonical records must byte-match this encoding. No host float repr or unspecified sorted-key serializer is an oracle.

Independent encoding examples: the object with keys z, a and values integer 2 and integer 1 encodes exactly `{"a":1,"z":2}` followed by LF; the same values inserted in reverse order produce the same bytes. String U+000A encodes as `"\u000a"`, not a short escape; Unicode é is emitted as UTF-8 c3 a9, while a metadata string containing e plus combining acute remains those distinct scalar bytes. For keys U+E000 and U+10000, U+E000 (UTF-8 ef 80 80) sorts first; U+10000 (f0 90 80 80) follows, distinguishing scalar order from UTF-16 surrogate ordering. Integers 1 and 9007199254740991 are accepted; JSON 1.0, 1e0, -0, and 9007199254740992 refuse. Request parsing must check numeric lexemes as well as decoded values, so a generic parser cannot silently turn -0 or 1e0 into an accepted integer. This numeric restriction deliberately replaces the earlier unspecified finite-float allowance in the proposed metadata design; the operator's manual acceptance includes that narrowing.

SnapshotManifest has exactly schema: castle.namespace_snapshot.v1, namespace_id, policy: NamePolicy, captured_revision, root_id, cas_binding: CasIdentity, origin (the closed capture/redacted union above), entries: array of complete EntryRecord sorted by entry_id ASCII UUID bytes. A capture includes the root exactly once and every live entry exactly once at captured_revision; a redacted view includes the retained rooted subset of that original capture. Neither contains tombstones or snapshot catalog self-reference. Inspectors must expose origin and must not label a redacted view a faithful full capture. Validate independent reachability/unique IDs/parent/name/content constraints before encoding. changed_revision is never greater than captured_revision. Snapshot size is the exact canonical byte count; CasID is SHA-256 of those bytes including LF. A request fingerprint is SHA-256 of canonical encoding of schema: castle.namespace_fingerprint.v1, namespace_id, expected_cas, expected_revision, kind and normalized args; sort sets, folder inventories by entry_id and duplicate maps by source_id as specified before encoding. All set-like arrays, inventories and duplicate maps accept arbitrary input order and normalize to the specified sort order before fingerprinting; duplicate keys/IDs refuse rather than collapse silently. This includes expire-results operation_ids and excision action/selection sets. Metadata object key order never changes semantic identity. Source transport location, session token, wall-clock timeout and file descriptor numbers are absent.

## 17. Bounded CAS publication and interruption repair

The proposed interface publish_namespace_content(cas_root, operation_root, expected_identity, publication) returns PublicationReceipt; recover_namespace_publication with those same arguments returns the same receipt or a fixed storage-recovery refusal. Publication is a closed durable record: schema: castle.namespace_publication.v1, namespace_id, operation_id, publication_id (NamespaceUUID), cas_binding, cas_id, size, staged_file_id, cas_temporary_relpath, prior_object_present, journal_prefix_length, journal_prefix_sha256, events, remotes and state. events is the exact ordered array of closed delivered journal-v2 records, with minted event IDs/timestamps recorded once and canonical line byte lengths/digests. remotes is the exact protected pre-publication multiset of all target-local remote rows, preserved with multiplicity; it is not silently dropped if index reading fails. state is prepared or complete. Receipt has exactly publication_id, operation_id, cas_binding, cas_id, size, event_ids, journal_length and journal_sha256. No record changes the CAS journal schema or introduces CAS-root recovery sidecars.

Acquire the namespace/domain fence before the CAS stable journal lock; hold the CAS lock across checking the strict complete prefix, event generation, durable evidence publication, object publication, append, index commit, and durable receipt. Record publication evidence before the first unsafe effect, including whether the object existed before this publication. cas_temporary_relpath is the exact shard-relative .cas-<publication UUID with hyphens removed>.tmp path (32 lowercase hex characters, matching the delivered transient classifier), persisted before exclusive creation; it is not inferred by scanning random filenames. The bounded publication path streams/copies staged bytes in its owning process and starts no copy subprocess/background writer. Acquire the delivered CAS stable/journal lock before minting event IDs, monotonic timestamps and stored/dedup outcome against the actual current tail. After crash, verify temp content and process-owned write quiescence; a free lock alone does not prove an unrelated surviving writer is gone. The exact staged bytes/size/digest, index/remotes snapshot, appendable journal prefix and current active member/epoch must match. Fsync each staged file/evidence file and operation directory before object rename/link; fsync every changed object directory before journal append; append the recorded event bytes, flush/fsync journal; reconstruct/verify the index fold and exact remotes in a durable transaction; fsync new index/directory entries as required; publish complete receipt by fsynced atomic replacement and directory fsync. Then release locks. Namespace commit requires the validated receipt, not the return of ordinary ingest_file alone. Multiple payloads in a folder have independent publication IDs under one namespace operation and a deterministic publication order; their evidence stays protected until resolution.

| Observed state after lock/reopen | Only admissible recovery |
|---|---|
| Prefix unchanged, no object/new temp only | Validate owned stage/receipt and resume original publication; clean only independently owned pre-intent residue when no intent exists. |
| Correct object exists, journal exactly saved prefix | Verify digest/size/sealing and ownership; append the saved events once, never mint new events. A pre-existing deduplicated object is retained and independently validated. |
| Journal ends in a strict byte prefix of recorded appended bytes | Verify the entire saved prefix length/digest and that every byte after it is exactly a prefix of this publication's saved event stream. Under the same lock truncate only this proven operation-owned suffix to the saved boundary, fsync, then append the complete saved stream and fsync. No unrelated valid or corrupt suffix is truncated. |
| Exact saved append complete, index stale/missing | A complete saved stream at the recorded boundary is already appended, even with additional valid strict events after it. Validate the entire journal/object inventory; preserve any such subsequent events. Reconstruct only the derived index with the exact remote multiset if its ownership/equality is proved; an unexplained later remote change blocks rather than overwriting it with a stale snapshot. No duplicate event/sighting is appended. |
| Receipt complete, namespace commit/response absent | Verify all receipt identities/events/content and index/remotes before handing the same receipt to namespace recovery. Never repeat the effect merely because the caller missed its response. |
| Tail that is neither an owned partial stream nor a complete saved stream followed by valid strict events, changed prefix/member/epoch, unreadable/lost remotes, missing evidence, wrong/corrupt object or unowned residue | Refuse namespace-storage-recovery-required and preserve evidence. Never guess repair, delete unknown bytes, replace a member with a replica, or roll back acknowledged authority. |

A publication can include zero new events only when the complete intended sighting/content effect is independently already present and the receipt records that verified no-op; it is not inferred from an equal object hash alone. An index cannot authorize an unjournaled object. Ordinary CAS consistency outside this bounded operation remains governed by delivered verification; this interface does not repair historic arbitrary corruption. Once complete evidence is retired after a resolved namespace commit, normal CAS integrity and lifecycle checks remain mandatory; a later missing object is corruption, not permission to recreate arbitrary data from an expired request.


For an incomplete publication, visible bytes or a later successful checkpoint never retroactively prove an earlier failed fsync durable. Recovery must establish a new durable write from the verified operation-owned staged bytes/events before issuing a receipt; merely reopening, checking a hash and syncing a fresh descriptor is insufficient. Where the qualified environment cannot perform that bounded fresh publication safely, a reported write-back/fsync failure remains storage-recovery-required until explicit storage intervention. Real short-write/fsync fault tests must distinguish this refusal from process-termination cases that can finish forward. No original failed call is relabeled successful from subsequent visibility.

## 18. Database replacement marker and forward completion

The protected replacement.json record is closed and selection-free: schema: castle.namespace_replacement.v1, namespace_id, operation_id, source_generation, target_generation, predecessor_cas: CasIdentity, successor_cas: CasIdentity, stage and image_digest. Generations are fresh NamespaceUUIDs, distinct; image_digest is null until a validated fresh database image has been fsynced, then SHA-256 of that image. No roots, selected CasIDs, names, selection fingerprints, recipes, row counts or raw error text appear in the marker. A database image digest is integrity evidence, not a digest of the removed selection. Marker stages are blocked, image-ready, database-published, cleanup-scanned, cleanup-verified and complete. Complete retains the generation/identity binding, never selected content. The only image artifacts are namespace.<target_generation>.sqlite.new and namespace.<source_generation>.sqlite.old; IDs and file kinds must match a validated marker before any disposal. Marker publication uses the exclusive owned replacement.<operation_id>.tmp, validated against the private intent and removed only after durable replacement; this recognized temporary is not authority by itself.

Before any retirement, commit and durably synchronize the private intent and service_state recovery-required first; then durably publish the blocked marker; only then call the delivered CAS excision. Missing marker plus pending intent means resume marker publication, never resume ordinary service. The private intent retains the previous complete marker (or its absence) for the proven abort path. Protected operation intent stores the exact selection, operation UUID reused for the delivered CAS excision call, expected predecessor, all sanitized replacement recipes, and commitments to both caller-supplied resolved predecessor and destination roots; then marks service recovery-required. Root commitments use the unchanged SHA-256 of each resolved-root string encoded as the canonical UTF-8 JSON string with its final LF. The hash input has no additional domain-separation prefix; distinct predecessor_root_commitment/successor_root_commitment SQL columns and validated namespace/operation/generation/epoch joins preserve the roles. Keep the original hashes in protected private intent and then in the selection-free SQL completion row, never in the marker. They are equality witnesses, not paths, authentication, routing or access grants. Predictable root paths remain susceptible to offline guessing and cross-record linkage; these unsalted hashes make no path-secrecy claim. Retain no selected names, content IDs, removed-selection fingerprints or private plaintext in completion. Every recovery call supplies both explicit roots again, reads only the exact marker-bound namespace control authority needed to validate the original commitments, then checks root safety and delivered identities before CAS payload I/O or cleanup; a different same-ID replica/path refuses even after private intent disposal. Missing proof refuses rather than deriving a new commitment from the current caller arguments. The caller retains its root-location routing. After cutover all ordinary calls require the explicit successor root and new expected identity; the namespace never discovers a destination from metadata. The pre-retirement marker is blocked with predecessor_cas equal successor_cas until the delivered cutover establishes a different successor. The operation intent, not a guessed marker edit, records the delivered excision binding and stage; recovering a predecessor-equal marker after retirement must validate the actual delivered retirement/successor receipt and update the marker durably while service remains blocked. Missing or mismatched durable operation authority refuses; marker absence never proves cleanup completion. Explicit abort-before-retirement first proves under the same ownership/CAS locks that source retirement is absent, predecessor authority is unchanged/consistent, no write remains in flight and the blocked marker belongs to this intent. Persist recovery_action abort-before-retirement while unavailable; restore the prior complete marker, or remove the new blocked marker if none existed, and fsync the directory; then durably commit rejected operation/ready predecessor state without advancing revision. A crash resumes this recorded abort before service. Any prepared successor is left fenced and explicitly reported as caller-owned residue; abort never deletes it or claims purge, and its later disposition requires caller authority. If any proof is missing or retirement is present, abort refuses and recovery stays forward-only. The previous complete marker is thus restored, not stranded behind an abandoned blocked marker. Before retirement, delivered excision request/root/destination/operation/source-consistency/unknown-selection errors translate to the corresponding safe namespace refusal or recovery-required when owned preparation remains; predecessor authority stays selected. excision-preparation-failed and excision-remotes-unreadable map to recovery-required while a durable intent remains. A validated building/prepared destination with no source retirement resumes the same excise_store arguments/UUID/selection; excision-preparation-incomplete does not authorize recover_excision as a new cutover. Unknown or unbound destination residue stays blocked for explicit storage intervention. Once retirement is present, excision-retirement-committed or excision-retirement-incomplete require the same bound recover_excision only; excision-recovery-state or mismatched evidence blocks service. Never decide rollback solely from an exception string: inspect the validated delivered retirement state under locks.

| blocked | Durable private intent/recipes and marker prevent service. Once database-published is durably established, later opens validate generation, logical authority and completion rows rather than comparing a legitimately mutated database with its old image digest. To start another replacement, require the previous marker complete, record the new private intent, and atomically replace the marker with a fresh operation/generation binding. Partial/unknown generations never overwrite a pending marker. Before retirement errors may abort without changing namespace revision, but after retirement the result is pending/recovery-required until complete; no restart reactivates the predecessor. Confidential cleanup claims remain bounded to the qualified adapter's owned artifacts; physical remanence, offline copies and already disclosed plaintext remain caller custody obligations.

## 19. Protected execution and refusal qualification

The caller supplies an environment-level authorized execution/filesystem capability, not an in-process replacement for Castle's CAS filesystem, clone, sealing or SQLite calls. No generic SQL/backend plugin, crypto product or attestation service is added. Existing CAS I/O runs unchanged inside the qualified environment. ProtectionMode is a closed union: {kind: unprotected} or {kind: protected, capability_id: nonempty opaque identifier}. Persist it at namespace creation. Unprotected local namespaces are supported but carry no encryption claim. Opening protected authority without its matching admitted capability refuses namespace-protection-unsupported; opening an unprotected namespace while claiming a protected capability also refuses rather than silently upgrading it. Protection-mode conversion requires separate explicit authorization and qualification.

AuthorizedSession is a caller-owned runtime protocol with acquire_domain_ownership() returning the caller-owned exclusive lifetime context manager, describe_capabilities() returning CapabilityDescriptor and check_authorized(operation_kind) returning normally or raising namespace-access-denied/namespace-session-expired. Call authorization before protected I/O and again before exposing bytes or acknowledging a durable outcome. CapabilityDescriptor has exactly capability_id (null in unprotected mode), protection_domain_id (nonempty opaque string), namespace_root, cas_root (resolved runtime-only paths), and properties (unique names from the closed set locking, path-safety, immutable-staging, durable-publication, sqlite-extra, restart-recovery, revocation, protected-artifacts, authorized-export). All but protected-artifacts are required in unprotected mode; protected mode requires all nine, matching capability_id and exact explicit roots/domain. Castle checks this shape, membership and binding; the caller's trusted environment evaluates and attests the truth of each property. A self-asserted descriptor is not authentication, and Castle cannot prove an attestation's truth. No credential/key material enters this record, persisted authority or logs. The capability binds the explicit namespace/CAS roots, protection domain, actual SQLite/runtime configuration, storage semantics and key/session lifetime. Admission must be based on caller-trusted environment evidence, not accepting an arbitrary capability-id string as authentication. The environment must provide stable process/thread locking, no-follow/exclusive creation, immutable staging, positional reads and locked truncation, atomic same-filesystem replacement, file/directory fsync, SQLite DELETE-journal EXTRA atomic/durable commits, restart recovery, handle draining, protected logs/sidecars/temp/backups/indexes and authorized export. Optional Darwin clone/sealing capabilities retain their existing platform refusals; protected mode never silently emulates a missing required guarantee. Check capabilities before opening protected bytes. Unsupported/missing properties refuse the affected deployment, not the unprotected synthetic test environment.

Within admitted protected execution, Castle can perform its existing path/SQL operations; unauthorized service/host processes outside that boundary must see ciphertext for names, manifests, pages, sidecars, intent/results, staging, journals, indexes and backups. Encrypting source blobs while leaving namespace SQLite plaintext is insufficient. Caller configuration identifies the environmental ownership and cleanup boundary; Castle neither installs an encryption driver nor rewrites all delivered I/O through a new adapter. Session/key handles are opaque runtime arguments and never persisted or logged.

Session revocation closes new admission first, drains/cancels authorized handles according to the caller's policy, prevents further plaintext reads/exports, and makes subsequent calls namespace-session-expired. It never erases durable intent or converts possible commit into failure-none. Restart requires a newly authorized session to unlock and validate authority; it cannot recover by logging secrets, copying plaintext into ordinary temp storage or reusing expired handles. Key acquisition, authentication and attestation are caller responsibilities; Castle does not read credentials or assert host memory/key destruction. A process killed mid-I/O is recovered through durable evidence in a new admitted execution context.

Independent environment-bound evidence must name the actual capability/storage/SQLite configuration and prove: two processes cannot both own mutation; concurrent clients and interrupted reads/commits preserve §15; every sync/replacement/truncation fault yields its durable boundary or refusal; restart/revocation do not widen access; unauthorized processes cannot read any covered artifacts; staging, sidecars, logs and backups remain protected; and purge scans/disposal survive interruption. Positive qualified fixtures and deliberately unsupported/unsafe fixtures must both exercise the intended admission/refusal. Synthetic plaintext local tests prove transactions, ownership and recovery mechanics only. No encrypted deployment claim follows without the owner's actual qualified environment evidence.

## 22. Delete and Excise caller closure

As of 2026-10-28, Delete removes live entries atomically while retaining CAS bytes, deleted entry payloads and ordinary operation logging. Excise removes the explicitly selected application-managed bytes and entry/metadata payloads through the existing successor epoch and fresh namespace generation. Selected directories include retained deleted descendants. Content-free entry or metadata cleanup is supported and still advances the epoch; an entirely empty namespace selection refuses. No physical-media overwriting, external-copy removal or automatic garbage collection follows.

The authorized read protocol adds inventory-excision with empty args and preview-excision with exactly operation_id, selection and snapshot_actions. Both return under the same serialized admission and SQL read consistency as ordinary reads, authorize excision-inventory before disclosure and bind their results to the enclosing revision and CAS identity. Inventory returns ExcisionInventory containing entries (HistoricalEntry with entry: EntryRecord and live: bool), snapshots (HistoricalSnapshot with view: SnapshotView and live: bool), operations (payload-bearing HistoricalOperation with operation_id and state; payload-free retired reservations are excluded), dependencies (ContentDependency with owner_kind, owner_id, cas_id and role), and content_ids. Each collection is complete and deterministically sorted, including deleted entries/catalog records and retained dependency owners. Snapshot membership is verified before disclosure. Raw operation requests/results/errors and physical paths are not returned. Each inventory collection is bounded separately to 100000 records; verified snapshot entry pairs across the inventory are additionally bounded to 100000, and the complete canonical value is bounded to 67108864 bytes. Payload-free permanent reservations do not consume these inventory owner bounds. Overflow refuses, never truncates or paginates implicitly. These finite complete-read limits are not a claim that every arbitrarily large historical store admits inventory whenever a smaller execution selection would fit. Callers must protect any inventory/preview output they retain: these authorized responses disclose historical names, metadata, identifiers, relationships and content hashes.

Preview requires an explicit current at_revision and a caller-chosen future operation UUID. It returns ExcisionPreview with request: MutationRequest or null, entry_ids, metadata_entry_ids and conflicting_content_ids (sorted unique retained CasIDs). The normalized proposed request expands selected retained directory descendants and includes disclosing operation-owner IDs computed by the same planner used for execution. It does not silently add content IDs, unrelated shared entry owners or snapshot actions. Uncovered content owners and missing exhaustive snapshot actions still refuse before effects. Conservative retained journal/remotes matches against removed names, metadata keys, string values and canonical scalar values, plus selected-CasID literals in retained journal/remotes fields or CAS objects, are reported as conflicting_content_ids by preview, with request null; execution retains its fixed dependency refusal. Selected-CasID literals in retained entry names, their persisted casefolded comparison keys or metadata, or in sanitized snapshot recipes, instead refuse namespace-dependency-conflict before intent in both preview and execution without naming owners; callers must explicitly remove or clear the remaining owners. IDs in this authorized diagnostic are not added to the selection and are not authority to remove innocent matching content. No paths, journal fields or raw operation payloads are returned. The caller explicitly executes the returned request only after accepting its full selection. Preview is not authorization, durable intent, token reservation, cleanup or an execution promise. Execution revalidates closure under current admission and exact revision/binding. Rejected and aborted operation payloads can change required closure without changing revision: dependency-conflict as well as revision-conflict requires a fresh preview, even at the same revision. Preview is not a reservation of those inputs. Before any UUID resolution, reservation lookup or historical read, both queries require excision-inventory authorization; excision-inventory-result authorization precedes return. The released shared excision planner already requires both excision-inventory and excision-inventory-result before its private closure may pass into execution or pre-retirement staging/abort recovery; those existing requirements remain intact and are reused by the new queries. Conflicting input refuses without poisoning a healthy handle; detected backing corruption remains recovery-required. Preview has exclusive full-store validation cost; content-free selection skips only the impossible literal-CasID match scan, not integrity or metadata-disclosure checks. No query stores selected material or changes SQL/CAS/files. Ordinary live listing and the explicit-root library excision boundary remain unchanged; the CLI adds only the two read transports.

The journal/remotes proxy compares whole fields and slash-separated components. Common metadata keys such as docs or scalar values such as 1 can therefore match innocent retained source paths and block entry or metadata-only excision. This deliberately conservative refusal has no in-scope override or automatic remedy: only an independently authorized explicit content selection can remove those retained sources, and a matching diagnostic itself grants no such authority. Do not broaden a purge merely to silence a refusal. Equal strings are not a claim about their original intent.
