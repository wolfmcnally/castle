# Content excision

This independently reviewed contract defines the successor-epoch excision implemented by `castle.store_state` and `castle.excision`. The [CAS contract](cas-api.md) and [grow-only merge semantics](crdt-semantics.md) identify the same extension and distinguish it from their historical pre-excision observations. Implementation status does not itself establish release qualification, completion of any real-store operation, external-copy removal or custody acceptance.

## 1. Scope, authorization, and terminology

As of 2026-09-05, the operator's ruling is: “You are authorized to implement excision.” Independent design review and executable qualification remain required. The [readiness brief](release-and-deployment-readiness.md#3-excision--successor-epoch-implementation) records the authorization and sequencing.

Excision accepts complete content identities, constructs a successor containing the retained authority, and retires the local predecessor. A **store identity** identifies one local replica; a **lineage identity** identifies a family; an **epoch identity** identifies one merge-compatible authority domain within that family. **Generation** counts predecessor transitions. **Retirement** is an irreversible local fence, followed by removal of the predecessor's content-bearing files. **Completion** means the bounded local postconditions in §6, not erasure of every physical copy.

The supported envelope is cooperative callers, quiescent local filesystem stores, and portable verified reconstruction on macOS and Linux. Consumers stop admission and drain readers, writers, and open database handles before preparation or excision and keep them drained until cutover completes. Stable locks order cooperative mutations; they cannot revoke external open file descriptors. No Windows qualification, remote deletion service, distributed consensus, hostile filesystem administrator, or concurrent-branch preservation is added.

## 2. Amendments to the delivered contract

| Pre-excision property | Reviewed amendment | Preserved boundary |
|---|---|---|
| Objects and journal events are grow-only authority. | Excision constructs a fresh epoch from retained authority, then retires its local predecessor. | No delete event, tombstone, or altered ingest-event grammar inside an epoch. |
| Store roots have no persisted epoch identity. | Every ordinary usable store requires the current closed identity metadata in §4. | Identity is never inferred from a path, content hash, or generation alone. |
| Merge unions any otherwise valid stores. | Both operands must be active members of the same epoch; retired and cross-epoch operations refuse before authority publication. | Within-epoch object/event union, target-local remotes, deterministic journal ordering, and conflict refusals remain. |
| Bootstrap can create missing store structure. | New empty stores receive identity metadata; existing unprepared stores require explicit offline preparation; a retirement marker always prevents recreation. | CLI absent-root guards and existing verification exit codes remain. |
| Clone carries the current store inventory. | Clone carries epoch membership but mints a distinct local store identity and fresh inert lock. | Darwin-only CoW, exclusion ordering, no object reads or index rebuild, no byte-copy fallback. |
| SQLite is reconstructible except for remotes. | Excision builds a new database from retained authority and filtered remotes, never a copied database with rows deleted. | Ordinary rebuild continues to preserve all remotes or refuse. |
| The package has one-way module initialization. | `castle.store_state` owns lifecycle validation and imports only the root error from `castle.journal`; journal entry points consult it through function-local imports after journal initialization. `castle.excision` imports journal, state, and CAS. | No runtime import of the isolated v1 reader; no compatibility exports from the package root. |

This is a contract amendment, not an in-place deletion feature. Ordinary journal-v2 schemas, event identity grammars, canonical serialization, ingest receipts, clone instrumentation, CLI command set, and verification results keep their delivered shapes. New lifecycle refusals are errors rather than new verify exit categories. Excision is library-only; no generic merge, copy, preparation, or excision CLI is added.

## 3. Library API

All signatures below are the exact public interfaces. Imports are from the named owning module. `Path` means `pathlib.Path`, `Sequence` means `collections.abc.Sequence`; strings are not accepted as a selection sequence. Public result types are frozen dataclasses with exactly the listed fields and a `to_dict(self) -> dict[str, object]` method producing their closed JSON representation. Construction validates the same field types and relationships as persisted parsing; callers cannot create a valid-looking result with an invalid identity or outcome. UUID values are supplied as canonical lowercase hyphenated UUIDv4 strings without a prefix; booleans are not integers.

| Owner and exact signature/type | Validation and result | Binding and mutation |
|---|---|---|
| `castle.store_state.StoreIdentity(store_id: str, lineage_id: str, epoch_id: str, generation: int, predecessor_epoch_id: str \| None)` | Exact identity fields and relationships in §4; no filesystem path. | Value type; complete equality binds an expected local source. |
| `castle.store_state.read_store_identity(store: Path) -> StoreIdentity` | Safe existing root and valid active metadata required; retired or inaccessible successor refuses. | Read-only; no enrollment or index opening. |

Existing `clone_store(source: Path, destination: Path, *, instrument: OperationSink | None = None) -> None` and `merge_into(target: Path, source: Path) -> None` keep their signatures. Existing merge-owned errors remain owned by `castle.store_merge`; new lifecycle codes use `StoreStateError`. No initialization token, query language, policy callback, alternate deletion mode, or global operation registry is exposed.

## 4. Closed persisted metadata

Every JSON metadata file below is UTF-8, sorted-key compact JSON with one trailing newline, no BOM, duplicate keys, unknown/missing fields, nonfinite numbers, or trailing values. UUIDs use the §3 grammar. Integers are nonnegative JSON integers, excluding booleans. Files must be safe regular single-link files; directories and locks retain the existing root/subtree safety rules. Parsers validate exact schemas and types before acting. No file's presence alone proves a valid transition, but presence of `retired.json`, even malformed, always fences ordinary access before any bootstrap.

### Identity and binding shapes

| Shape | Exact required fields and types | Relationships |
|---|---|---|
| Identity (`StoreIdentity.to_dict()`) | `store_id: UUID`, `lineage_id: UUID`, `epoch_id: UUID`, `generation: integer`, `predecessor_epoch_id: UUID or null` | Generation 0 has null predecessor; positive generation has a nonnull predecessor distinct from its epoch. Fresh store, lineage, and epoch UUIDs are independently minted. |
| Transition binding | `operation_id: UUID`, `predecessor: Identity`, `successor: Identity` | Same lineage; successor generation is predecessor generation +1; successor predecessor-epoch equals predecessor epoch; different store and epoch UUIDs. Operation UUID is non-content-derived and distinct from these identity UUIDs. All copies of this binding must be exactly equal. |

### Files and publication owners

| Exact filename and schema | Exact closed fields | Allowed values, ownership, and lifetime |
|---|---|---|
| `store.json`, `castle.store.v1` | `schema: string`, `identity: Identity`, `state: string`, `transition: Binding or null`, `prepared_sha256: string or null` | `state` is `building`, `prepared`, or `active`. Bootstrap/preparation writes active with null transition. Excision alone writes building/prepared with a binding whose successor equals identity, then active with that same binding. Active with null transition is also the clone shape. `prepared_sha256` is a complete lowercase SHA-256 identity only in prepared state; it is required null in building/active. Identity is immutable for this local root. |
| `excision-selection.json`, `castle.excision_selection.v1` | `schema: string`, `transition: Binding`, `cas_ids: array[string]` | Nonempty lexicographically sorted distinct complete content identities; binding equals destination `store.json`. Private preparation data at the destination only, mode 0600. Needed to validate pre-retirement request retry; never consulted for post-retirement deletion. Remove before completion. |
| `retired.json`, `castle.retirement.v1` | `schema: string`, `transition: Binding`, `state: string` | At predecessor only; `state` is `retired` or `complete`. Excision publishes `retired` at the irreversible boundary, later atomically replaces it with `complete`. Binding predecessor equals original source identity. This marker supersedes any surviving source `store.json`. Never remove it or restore active state. |

`store.json` is the sole ordinary epoch authority. A successor's transition is content-free provenance, not an ingest event. `retired.json` is the sole local retirement authority and, at `complete`, the durable receipt source. No selected digest, journal digest, event ID, path, name, source label, remote key, reason, count, timestamp, or consumer record belongs in identity or transition fields. Only the explicitly temporary selection contains selected hashes. No separate audit log, selection digest in a receipt, or ancestry list is added.

The temporary `prepared_sha256` seals retained payload for recovery after source authority is removed. Its preimage is canonical sorted-key compact UTF-8 JSON with one trailing newline and exactly three fields: `objects` is the lexicographically identity-sorted array of `[cas_id, integer_size]` pairs; `journal_sha256` is the complete SHA-256 identity of canonical retained journal bytes; `remotes` is the lexicographically sorted array of five-string rows in delivered column order, including duplicates. Recompute from actual verified destination objects, journal and database rows, not from an earlier in-memory plan; also verify the derived tables against the journal fold. Compare before every prepared-to-active transition, including recovery. A mismatch is recovery-state, never permission to rebuild after retirement. Atomic activation replaces this digest with null; no content-derived seal survives in active metadata or the receipt. Building state has no trusted seal and must be reconstructed from the locked source.

Metadata publication means: create a private same-directory temporary regular file exclusively; write canonical bytes; flush and fsync; parse/read back exact expected bytes; atomically publish without adopting an unrelated target; fsync the containing directory. Replacements are allowed only for an already validated file owned by the current operation. Temporary metadata names are fixed per target: `.store.json.tmp`, `.excision-selection.json.tmp`, `.retired.json.tmp`. A bound operation may remove these regular single-link residue files; an unbound or unsafe residue refuses. On supported filesystems, failed fsync is a failed publication, never a successful result.

A clone validates active source metadata under the stable source lock, preserves lineage, epoch, generation and predecessor-epoch, mints only its local store UUID, writes active metadata with null transition, and preserves the existing no-object-read cost contract. It never copies retirement, preparation selection, or metadata temporary files. Within-epoch merge compares `(lineage_id, epoch_id, generation, predecessor_epoch_id)` under both stable locks before publishing any object or journal. Different epoch or lineage refuses in either direction; equal epoch with contradictory generation/predecessor is invalid metadata. Store UUID equality at distinct roots refuses as an aliased identity. Same generation with different epoch is never compatible. Disconnected replicas receive no remote retirement notification; their old epoch prevents merge into a successor but does not prevent their own continued use by an uninformed caller.

For example, valid initial metadata is `{"schema":"castle.store.v1","identity":{"store_id":"11111111-1111-4111-8111-111111111111","lineage_id":"22222222-2222-4222-8222-222222222222","epoch_id":"33333333-3333-4333-8333-333333333333","generation":0,"predecessor_epoch_id":null},"state":"active","transition":null,"prepared_sha256":null}` before canonical key sorting. Changing state to prepared while leaving transition and seal null is invalid; adding an unknown field or using a generation-zero nonnull predecessor is also invalid. A retirement marker has exactly its schema, the full §4 binding, and retired/complete state; an identity-shaped object without that binding cannot authorize cleanup.

## 5. Selection and successor construction

Normalize duplicates without altering identity syntax. Reject an empty sequence, a string/bytes in place of a sequence, non-string members, uppercase or unprefixed digests, and anything other than `sha256:<64 lowercase hex>`. Select by identity only, never by filename, document status, substring, source label, or consumer record. Every selected identity must be in both the object inventory and the valid journal fold. An otherwise valid source with any unknown member refuses the whole selection before retirement; there is no partial success. A journal-only or object-only member is source inconsistency, even if other selected members exist. Removing every object is allowed and yields a valid empty successor.

Before creating the destination, validate the full source journal using strict v2 parsing, sequence validation and index fold; inventory every object; stream-check every digest and size; require exact inventory/fold agreement and safe sealed object posture; read remotes without writing the source database. A present unreadable database or remotes table refuses. An absent database means no remote rows, as in ordinary rebuild. Index drift in journal-derived tables does not justify carrying those tables; reconstruct them from authority. A remote row naming no source object is inconsistent source metadata and refuses. Safety checks reject unexpected root entries, symlinks within either subtree, special files, hardlinked content-bearing files, and overlapping roots. Ancestor symlinks outside a store remain allowed and canonicalized once.

| Successor surface | Exact transformation and independent validation |
|---|---|
| Objects | Copy every unselected object to its identity-derived path, stream-verify destination digest and bytes against source, preserve content identity, reseal under supported posture; copy no selected object. No hardlink or whole-store clone. |
| `journal.jsonl` | Keep every event whose `cas_id` is unselected, including all retained sightings and refinements; preserve every field and event ID; emit canonical ordering/bytes. Remove all events for selected identities, including deduplicated sightings. Validate the complete retained sequence and fold. |
| `cas.sqlite` | Create a new database and schema, insert only retained fold rows, and verify actual rows independently against the fold. Never copy source database pages and delete rows. |
| `remotes` | Retain precisely rows whose identity is unselected; preserve all five values and duplicate multiplicity with multiset comparison. Do not union replicas or contact any remote. |
| Sidecars and residue | Never carry predecessor WAL, SHM, rollback journal, or temporary database files. Close/checkpoint the newly created database, remove its owned temporary/sidecar files, fsync payload and directories, then validate a clean inventory before prepared publication. |

Portable excision uses verified byte reconstruction and can cross devices; it does not invoke Darwin-only store cloning or inherit clone's no-object-read promise. On Darwin, carry any declared sync exclusions to the empty successor and verify them before writing payload, and enforce the corresponding supported sealed posture. On Linux, require ordinary read-only object sealing without asserting APFS capabilities. Refuse an unsupported required posture before retirement. Temporary reconstruction stays in the bound destination; no content-bearing staging files elsewhere are authorized. Source remotes are read through a read-only connection with drained handles; no source checkpoint or opportunistic repair is allowed.

SQLite's [secure-delete excerpt](../docs/sqlite-secure-delete.txt) describes setting-dependent residual traces and virtual-table limitations (As of 2026-06-04; Retrieved 2026-09-06). The design inference is to avoid importing predecessor database residue at all. Fresh reconstruction and unlinking establish the named local file result; they do not establish media overwrite, SSD sanitization, snapshot destruction, or global erasure.

Reconstruction writes payload directly at its final relative paths inside the inaccessible building destination: `objects/sha256/...`, `journal.jsonl`, and the newly created `cas.sqlite`. It introduces no separate content staging directory. The only admitted database residue names are `cas.sqlite-wal`, `cas.sqlite-shm`, and `cas.sqlite-journal`; the metadata temporary names are specified in §4. All remote values must be strings in the existing five-column order; malformed values refuse as source-inconsistent rather than being coerced or omitted. Rebuilding an owned prepared destination first durably replaces its state with building and its seal with null, before removing/replacing payload; the saved selection and binding remain for the restart. These rules make residue ownership and interrupted reconstruction observable without another recovery manifest.

## 6. Publication, retirement, and recovery

Acquire existing stable locks without any bootstrap-capable helper for retirement/recovery; never replace or unlink the predecessor `journal.lock` inode. Hold the predecessor lock from final validation through preparation, retirement, cleanup and receipt. Once a destination exists, hold its fresh stable lock too; order two-root acquisition by canonical root path and revalidate the source after acquisition. Ordinary mutation waiters recheck lifecycle after acquiring their lock, before opening or creating authority. The external quiescence requirement covers readers that do not retain a lock for their entire read.

This is not an atomic transaction across trees. Each row below names a durable boundary. Interruption before or after every metadata rename and directory fsync must be classified from observed validated state on retry, not from the last instruction attempted. A visible retirement marker fences immediately even if its preceding call failed to confirm durability. Before that fence the source remains authority; afterward recovery never rolls it back. New excision admission on a source also requires no prior incomplete operation at its supplied destination; callers serialize operations and retain the operation/root association outside Castle.

| State/boundary | Durable evidence and ordinary operations | Retry/recovery action and cleanup |
|---|---|---|
| Unprepared existing v2 source | Valid v2 authority, no `store.json`, no retirement. Ordinary runtime refuses identity-required. | Offline `prepare_store` validates and publishes active identity; preserves existing payload. A crash before identity publication leaves authority intact. Without residue, preparation is repeatable; an unpublished unbound metadata temporary file refuses state-invalid and requires separate residue resolution. Once valid identity metadata is published, retry validates and fsyncs that same identity rather than minting another. |
| Active predecessor, absent destination | Valid active `store.json`, no retirement. Source may operate subject to caller's quiescence. | Validate all inputs, lock and revalidate; mint successor and exclusively allocate destination. Refusal changes no source authority. |
| Allocated, unbound destination | Crash after exclusive mkdir/lock allocation but before valid building metadata. Source active, destination unusable. | Fail closed with destination-unowned; never infer ownership from its name or emptiness. Caller must resolve this disposable residue separately before retry. No automated deletion or adoption. |
| Bound building destination | Destination `store.json` is building with full binding; selection publication may still be absent/torn. Source active, destination refuses all ordinary operations. | `recover_excision` reports preparation-incomplete without mutation. `excise_store` with the same operation/source validates any present selection; if absent and no payload was yet written it may write the supplied selection. Otherwise missing/malformed selection refuses recovery-state. Reconstruct only owned payload from the current locked source. |
| Fully prepared successor | Destination prepared metadata and retained-payload seal published only after selection and complete retained payload verification and fsync. Source still active; destination remains unavailable. | Before retirement, `recover_excision` still reports preparation-incomplete. `excise_store` must match saved normalized selection, revalidate source, and rebuild/reverify retained payload before advancing; never trust stale preparation after a lock gap. |
| Predecessor fenced | Source `retired.json` with state retired and exact binding is published and directory-fsynced. Fully prepared destination still unavailable. | Commit point. Recovery compares destination prepared identity/binding and revalidates retained payload without selected identities, then proceeds forward. Missing/damaged successor or conflicting binding refuses; source stays retired. |
| Local cleanup in progress | Source retirement marker remains; source objects/journal/database may be partially removed. Destination stays prepared. | Delete predecessor owned payload and destination selection/residue idempotently, never following links. Post-retirement faults report retirement-incomplete. No re-ingest, old-epoch merge, source bootstrap, or source restoration. |
| Successor activation | Source contains only valid retired marker and original inert lock; destination contains only retained objects, canonical journal, fresh database, prepared metadata and fresh lock. All deletions directory-fsynced. | Atomically replace destination metadata with active, fsync, read back and validate identity. Recovery from prepared repeats activation; from active checks binding and cleanup without comparing to deleted source content. |
| Completed local transition | Source marker replaced with state complete and fsynced after activation and cleanup checks. Source inventory exactly `retired.json`, `journal.lock`; destination active and validated at completion. | Return §8 receipt. Completed `recover_excision` validates complete marker and supplied operation/expected source; it checks destination identity (active or its later retirement marker), returns the same historical receipt, and changes neither store. It does not claim the successor remains unmodified forever. |

The allowed bound pairs are active predecessor with building/prepared successor before retirement, retired predecessor with prepared/active successor during forward recovery, and complete predecessor with the matching active or subsequently retired successor for historical receipt retry. Missing successor after retirement, building successor after retirement, active successor without predecessor retirement, or any conflicting identity/binding is recovery-state. Retirement is never inferred from the successor alone.

Keeping the successor unavailable through cleanup is stronger than merely publishing after retirement: no newly admitted work can race with the completion checks. If a crash occurs after activation but before completion marking, recovery allows subsequent valid within-epoch growth, validates the successor's current consistent authority and binding, and finishes the predecessor marker; it never replaces active successor payload. Another excision of that successor is not admitted until its predecessor transition is complete, as recorded by the consumer's serialized workflow; bypassing that quiescent workflow is outside the supported cutover.

Post-retirement cleanup removes all predecessor objects, journal events, database, sidecars, source `store.json`, and owned metadata residue; unseal only the files being removed, preserve the stable lock, and fsync affected directories. The allowed predecessor inventory is established before retirement: ordinary object hierarchy, journal, index with recognized sidecars, store metadata and lock. Unknown files or new unsafe entries never become recursively deletable merely because a retirement marker exists. Encountering one stops with retirement-incomplete; it does not delete an unrelated entry. Selection and reconstruction residue at the successor is removed before activation. Completion retains no selected identities. Memory-held selections have operation lifetime only; Castle neither logs them nor promises physical memory sanitization.

Recovery binds explicit roots to the metadata, not the converse: no paths are persisted and no path is discovered from a receipt. The caller supplies both roots and the expected predecessor identity each time. Reject a different operation, predecessor, destination identity, generation relationship, or same-ID replica substitution before deletion. Valid bindings are cooperative local evidence, not cryptographic protection against a hostile administrator copying metadata. A missing predecessor marker is never proof of successful retirement; a missing destination is never recreated after retirement. After fencing, inspect the predecessor only for structural safety, binding and cleanup inventory: do not require its now-partial journal/object fold to be consistent, read its removed selection, or reconstruct any successor bytes from it. The prepared successor and its validated seal supply recovery's retained authority.

Ordinary reads, journal append, ingest, materialize, statistics, names/find, verify, rebuild, bootstrap/init, migration, clone and merge must refuse retired roots. Pure identity-to-object-path helpers remain pure and do not authorize I/O. Raw filesystem access and already-open descriptors remain outside Castle's enforcement. Retain the predecessor marker at its root for as long as any caller could reopen that root; deleting the marker is not part of this API.

## 7. Refusal identities and disclosure

For new operations, evaluate root safety first, then argument shape, then retirement/lifecycle and operation binding, then source consistency/remotes, then selection membership, then publication. Existing clone/merge root, overlap, device and safe-lock refusal ordering remains before the existing unsupported-platform check; Linux still refuses clone/merge before reading journal, metadata or object authority. On supported platforms lifecycle/epoch validation runs under stable locks before authority publication and before ordinary content comparisons. Existing migration expected-digest/parsing ordering is preserved after the added root/lifecycle check.

All new errors expose only the fixed code below. Suppress underlying exception chaining at public/CLI display boundaries; no selected digest, path, SQL text, filename, remote row, or free-form cause is printable. Callers know the roots and operation they supplied; they may keep private associations in their own controlled records. Existing ordinary diagnostics are not globally rewritten; failures crossing preparation/excision/recovery are translated into this closed vocabulary.

| Code (owning error) | Trigger and precedence within its class | Mutation already possible; next action |
|---|---|---|
| `excision-root-unsafe` (`ExcisionError`) | Missing source/parent, symlink root or unsafe subtree/lock, overlap, alias, unsupported required sealing; first applicable root safety check. | None before allocation; after fencing classify cleanup fault as retirement-incomplete. Correct roots/posture offline. |
| `excision-request-invalid` (`ExcisionError`) | Invalid operation UUID, expected identity, selection container/member, or empty selection. | None; correct request. |
| `store-retired` (`StoreStateError`) | Any present retirement marker at an ordinary entry point, regardless of residual active metadata. | None; use bound recovery or successor. |
| `store-identity-required` (`StoreStateError`) | Existing populated root lacks current metadata and has no retirement marker. | None; deliberate offline preparation only. |
| `store-state-invalid` (`StoreStateError`) | Unsafe/malformed/unknown-schema metadata, inconsistent identity relationship, or contradictory same-epoch metadata. | None; inspect offline, never infer an identity. |
| `store-not-active` (`StoreStateError`) | Valid building/prepared metadata at an ordinary entry point. | None; finish excision/recovery. |
| `store-epoch-mismatch` (`StoreStateError`) | Active clone/merge participants have different lineage or epoch. | No authority publication; retire stale copies outside Castle instead of reconciliation. |
| `store-identity-aliased` (`StoreStateError`) | Distinct participating roots assert the same local store UUID. | None; resolve copy ownership offline. |
| `excision-destination-unowned` (`ExcisionError`) | Existing destination has no valid excision binding, including an empty directory or ordinary unrelated active store. A valid but different binding uses operation-mismatch instead. | Never adopt/delete it; separately resolve destination. |
| `excision-operation-mismatch` (`ExcisionError`) | Expected source mismatch, different operation/bound successor, or different saved selection on a pre-retirement retry. | None on retry; supply the original request or correct roots. |
| `excision-source-inconsistent` (`ExcisionError`) | Invalid journal/fold, corrupt/missing/extra object, size disagreement or dangling remote identity. Checked before unknown selection. | No retirement; existing owned preparation may remain. Repair source in its owning workflow. |
| `excision-remotes-unreadable` (`ExcisionError`) | Present index/remotes cannot be read without mutation. | No retirement; do not silently drop remote rows. |
| `excision-selection-unknown` (`ExcisionError`) | Any requested ID absent from otherwise consistent source authority, including mixed known/unknown requests. | No retirement and no partial removal; correct whole selection. |
| `excision-preparation-incomplete` (`ExcisionError`) | Recovery called before a valid committed retirement. | None by recovery; retry `excise_store` with original selection. |
| `excision-recovery-state` (`ExcisionError`) | Malformed retirement/binding, missing or damaged prepared successor, impossible state pair, malformed selection before retirement. | Preserve observed state; no rollback or blind deletion. Operator resolves evidence/storage fault. |
| `excision-retirement-committed` (`ExcisionError`) | `excise_store` sees this operation's valid retirement marker, including complete. | No new work; call selection-free `recover_excision`. |
| `excision-preparation-failed` (`ExcisionError`) | I/O, verification or durability failure before any retirement marker is visible, after more specific input checks. | Owned incomplete destination may remain, source authority preserved; retry original request. |
| `excision-retirement-incomplete` (`ExcisionError`) | I/O, cleanup, activation, completion-marker or durability failure with a visible retirement fence. | Predecessor remains retired, cleanup/publication may be partial; call recovery, never reactivate source. |
| `store-preparation-failed` (`StoreStateError`) | Offline identity preparation validation/I/O fails and no more specific state/root error applies. | Existing authority unchanged; identity publication may be visible after a durability error. Retry preparation revalidates rather than minting over valid metadata. |

Offline `prepare_store` uses `StoreStateError`: root/authority/remotes failures become `store-preparation-failed`, while retired, required lifecycle, and invalid metadata retain their specific codes. `recover_excision` interprets valid retirement before the ordinary store-retired guard; malformed retirement yields recovery-state and still fences ordinary use. Recovery-state/binding refusals precede all cleanup. In excision, a valid matching retirement is recognized before trying to read deleted source authority or looking for selected IDs. Exact precedence and non-mutation are executable proof obligations.

## 8. Receipt schema and privacy

| Field | Exact type/value | Claim |
|---|---|---|
| `schema` | String `castle.excision_receipt.v1` | Closed schema identifier. |
| `operation_id` | Canonical UUIDv4 | Non-content-derived invocation identity, equal to binding. |
| `predecessor` | Identity object, exactly §4 fields | The locally retired replica and old epoch. |
| `successor` | Identity object, exactly §4 fields | The newly constructed replica and epoch at completion. |
| `outcome` | String `completed` only | No failed, partial, or global-erasure receipt exists. |
| `local_result` | String `successor-active-predecessor-retired` only | At completion: retained successor validated and active; predecessor payload and owned selection/residue removed; retirement marker retained. |

All six fields are required and nonnull; only the nested generation-zero predecessor-epoch field may be null. Receipt identities must satisfy the transition relationships. `recover_excision` reconstructs this receipt from the complete retirement marker without advancing generation or changing outcome to “already completed.” Equality of its canonical serialization is the retry stability check. The marker witnesses the historical transition; later authorized successor writes do not retroactively invalidate that receipt.

Illustrative valid receipt using invented identities:

```json
{"schema":"castle.excision_receipt.v1","operation_id":"66666666-6666-4666-8666-666666666666","predecessor":{"store_id":"11111111-1111-4111-8111-111111111111","lineage_id":"22222222-2222-4222-8222-222222222222","epoch_id":"33333333-3333-4333-8333-333333333333","generation":0,"predecessor_epoch_id":null},"successor":{"store_id":"44444444-4444-4444-8444-444444444444","lineage_id":"22222222-2222-4222-8222-222222222222","epoch_id":"55555555-5555-4555-8555-555555555555","generation":1,"predecessor_epoch_id":"33333333-3333-4333-8333-333333333333"},"outcome":"completed","local_result":"successor-active-predecessor-retired"}
```

The example is readable JSON, not sorted-key persisted serialization. Invalid examples are the same object with any of these changes: add `cas_ids: []` (unknown/content-selection field); add `reason: "withdrawn example"` (free text); set `outcome: "physically-erased"` (unknown and overbroad claim); set successor generation to 0 (invalid predecessor relationship); remove `local_result` (missing required claim); encode generation as `true` (wrong type). A receipt with only the correct keys but an invalid relationship still refuses.

No selected content hash, journal digest, event identity, filename, path, source identifier, remote key, document identifier, free-form reason, raw exception, or item count is retained in a completed receipt. Fixed fields cannot attest which private document was selected. The consumer owns that association; Castle neither accepts nor stores it. No content-dependent data is sent to external services by this API.

## 9. Existing stores and serial-consumer integration

Existing valid journal-v2 stores are deliberately prepared offline, with payload validation and unchanged authority. Ordinary reads and merge never enroll a store silently, and there is no ordinary metadata-free mode. Separate preparation of disconnected metadata-free stores mints unrelated lineages: it is not a means of proving they once belonged together. Prepare the chosen source once, then make fresh supported clones if replicas are required. Preparation does not read v1; the existing isolated once-only v1 tool may first produce valid v2 at its explicit boundary, after which offline preparation adds identity. That tool checks retirement before journal access; no new legacy reader is added. Its explicit metadata-free migration path acquires the existing lock without ordinary bootstrap and reconstructs the validated v2 index through an internal authority-based helper, rather than the public active-store rebuild entry point. If its post-publication rebuild fails, the isolated tool reports the existing failure; prepare the now-v2 store deliberately before invoking ordinary rebuild. Prepared/retired stores never enter that path, and a valid active metadata-bearing v2 store still fails the existing once-only check.

Every document withdrawal in a serial consumer must invoke excision as part of the withdrawal workflow. The consumer accepts epoch advancement and updates all retained live references. It resolves shared-content ownership first: selecting one identity removes all identical bytes and all sightings in this store, not one document's share while retaining another's identical bytes. Castle does not decide whether that consequence is acceptable.

| Consumer-owned stage | Castle interaction | Completion/failure boundary |
|---|---|---|
| Record intent and stop admission | Consumer records withdrawal intent, roots, operation UUID, expected identity and selected content IDs privately; drains store users and open handles. | Withdrawal is pending; marking a document hidden is not excision. |
| Construct and retire | Invoke `excise_store`; after committed-retirement interruption invoke selection-free recovery with the original operation/source binding. | A Castle error keeps withdrawal incomplete. Do not reopen retired roots or select an unrelated destination. |
| Update consumer state | On local completion, atomically update whatever the consumer's own database supports: retained live CAS references, withdrawn records and search/original-copy handling. | No cross-database transaction is promised. Consumer failure after Castle completion resumes this stage using its durable operation association and stable receipt. |
| Reopen service and close intent | Confirm current references target the successor; report external-copy duties separately. | Consumer alone declares its withdrawal workflow complete; Castle's receipt cannot do so. |
| One-time historical backfill | Consumer selects previously withdrawn documents from its own authority, resolves shared content, records progress, and applies the same serialized workflow in resumable batches. | No concurrent-branch preservation is required; already-completed batches resume consumer bookkeeping instead of excising unknown IDs again. Castle never discovers the withdrawn population. |

Consumer records, original copies, indexes outside Castle, and correspondence between withdrawal and operation remain outside Castle. Failed reference updates must be visible as incomplete withdrawal/backfill even when local excision succeeded. No consumer name, filesystem path, private corpus example, or document identifier enters this upstream contract.

## 10. Alternatives and tradeoffs

| Alternative | Consequence |
|---|---|
| Filter only the index | Object and journal authority remain; rebuild restores the view. |
| Unlink selected objects only | Journal authority becomes inconsistent; stale union can restore bytes. |
| Append withdrawal events or tombstones | Sensitive authority remains; changes grow-only semantics without meeting removal. |
| Distributed deletion reconciliation | Adds coordination and conflict semantics unnecessary for the authorized serial consumer. |
| Construct successor and retire predecessor | Preserves within-epoch union; costs full retained-content reads/copies, temporary disk capacity, downtime, explicit reference updates and external-copy custody work. |

No global deletion guarantee is inferred from epoch fencing: an offline replica can keep its old content, and deliberately re-ingesting bytes into the successor is possible. The caller's selection and custody rules prevent those actions where required. An epoch is a merge fence, not a denylist of forbidden future content.

## 11. Behavioral falsifiers

Each property is tested against explicit independent fixture authority, not an API's own summary of success. Mutations below name what must turn its proof red; structural schema checks alone do not prove safe excision.

| Property | Independent oracle and falsifier |
|---|---|
| Complete removal | Enumerate successor object identities and parse all journal events; compare with source set difference. Retain one selected object or deduplicated sighting: fail. |
| Retention | Compare retained bytes, complete event records/order and remote-row multisets against source fixtures, with repeated sightings/refinements/remotes. Drop or change any retained value: fail. |
| Fresh derived state | Seed distinctive removed-only markers in predecessor database pages/sidecars, trace destination construction, inspect final files and derived rows. Copy predecessor database instead of creating fresh state, or leave owned selection/temp residue: fail. |
| Selection atomicity | Exercise empty/malformed, duplicate, all-selected, unknown and partly present selections. Allow partial success for mixed known/unknown input or remove only one sighting: fail. |
| Epoch equality and laws | Same-epoch clones retain ordinary union proofs; independent same-generation successors differ in epoch. Admit old/new merge in either direction or compare only generation: fail; break commutativity, associativity, deterministic bytes or idempotence: fail. |
| Lifecycle coverage | Invoke every root-touching library/CLI path on retired and prepared stores, including init/bootstrap and migration, with before/after inventories. Recreate journal/index beneath retirement, or read content from a prepared successor: fail. |
| Ordering and recovery | Interrupt before/after every durable boundary in §6, including allocation before binding and activation before complete marker. Publish active before fence, roll back retirement, delete an unowned root, overwrite active successor, or advance generation twice: fail. |
| Destination ownership | Replace destination/binding/operation/source expectation with an unrelated fixture; preserve its bytes on refusal. Adopt by name or skip full binding comparison: fail. |
| Privacy | Assert exact receipt/error representations and scan controlled sensitive tokens with positive controls. Add a selected digest, path, marker, count, or exception text: fail. |
| Platform and locking | On Linux exercise real byte reconstruction and exact clone/merge early refusal; on Darwin preserve exclusion/sealing/clone cost checks. Invoke Darwin-only native clone during excision or omit post-lock lifecycle recheck: fail. |
| Preparation | Validate pre-existing v2 stores and independent metadata fixtures; compare original journal/object/database bytes. Silently enroll on read/merge, preserve a metadata-free ordinary mode, or alter authority during preparation: fail. |
| Consumer isolation | Inspect package inputs/imports and disposable serial usage. Require consumer records, hidden concurrent-branch preservation, or a consumer database update inside Castle: reject. |

“Lookup returns absent” scores a query projection and can pass while selected authority or database residue survives. Pair it with inventories and controlled markers. Marker scans score string presence, not ownership: retained content may innocently contain the same text, so a positive match can invert the conclusion by identifying content that must be preserved. Use removed-only positive-control markers in disposable fixtures; use explicit identities for real selection. Neither byte scanning nor a content-free receipt proves which private document a consumer intended to withdraw.

## 12. Manual custody protocol

Before any separately authorized real operation, the store operator and consumer owner record the selected scope and shared-content consequence in their private custody surface, inventory known copies, assign a responsible party and outcome/evidence for each, and identify unresolved copies. Do not place that inventory or selected identities in Castle's receipt or repository.

| Custody surface | Responsible party and evidence to obtain |
|---|---|
| Local predecessor/successor | Store operator: explicit roots/identity association, drained handles, local receipt, retained references and named local postconditions. Keep retirement fence in place. |
| Consumer records, search indexes, retained originals and exports | Consumer owner: withdrawal/backfill progress, reference cutover, original-copy scope and any incomplete application updates. |
| Disconnected replicas and development copies | Each copy's custodian: retire or replace stale copies and prevent reintroduction; Castle does not enumerate or notify them. |
| Backups, filesystem snapshots and remote object versions | Backup/storage owner: identify retention and restoration paths, deletion/expiry evidence and unresolved retained copies. Local unlink does not cover them. |
| Storage retention and underlying media | Storage provider/operator: applicable retention and sanitization process, any pending expiry or unverified physical-media claim. No inference from an empty directory. |
| Encryption keys where applicable | Key custodian: actual key/copy scope and destruction evidence where cryptographic erasure is the chosen custody mechanism. Do not infer key destruction from object deletion. |

Review local completion separately from each external obligation. Record unresolved copies as unresolved, with responsible parties and next actions; never convert absence of visibility into proof of erasure. The contract review may assess whether this protocol assigns responsibility adequately; it performs no live-copy inventory, deletion, physical-erasure certification, or custody acceptance.
